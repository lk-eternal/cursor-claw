## 背景与问题

cursor-claw 为 Electron 桌面应用，macOS 安装包（dmg 等）依赖 electron-builder 完成构建。当前开发者在本机出包时存在以下痛点：

- **入口分散**：打包相关能力分散在 package.json 中的多条 npm 命令及 scripts/ 下若干辅助脚本，缺少面向「我要在本机打 mac 包」的统一入口。
- **缺少前置校验**：环境不满足（Node 版本不符、必要工具缺失、签名/公证相关前置未就绪等）时，往往在打包流程中途才暴露问题，排查成本高、等待时间长。
- **版本号管理不直观**：出包时若需指定版本，缺少与日常开发习惯一致的明确方式；默认情况下应能沿用项目当前版本信息，避免手工多处修改。

上述问题主要影响在本机手动打包的开发与发布人员，不影响最终用户安装体验，但会拖慢本地验证与发版准备效率。

## 目标用户

- **本机开发/发布人员**：需要在 macOS 上为 cursor-claw 生成本地安装包（dmg 等），用于自测、内部分发或发版前验证。
- **使用方式**：以开发者在本机终端手动触发为主；非 CI 自动化流水线场景。

## 目标与非目标

### 目标

1. 在 `scripts/deploy/` 下提供 **macOS 本地一键打包**能力，封装现有 electron-builder mac 打包流程，降低记忆成本与操作步骤。
2. 打包开始前进行 **环境与依赖检查**，在失败前给出可理解的提示，说明缺什么、建议如何补齐。
3. 支持 **版本号**：默认读取项目当前版本信息；允许在触发打包时 **显式指定版本号**（可调整默认行为）。
4. **产出物与现有一致**：安装包形态、架构覆盖（x64 + arm64）、输出目录（`release/`）等与现有 mac 打包结果保持一致，不改变用户侧安装体验。
5. **与现有 npm 命令协同**：保留 `dist:mac`、`pack:mac` 等 npm 命令作为薄封装入口，底层统一走 deploy 脚本，使「npm 命令」与「直接调用 deploy 脚本」体验一致或更清晰（具体封装方式可在设计阶段细化，默认可调整）。

### 非目标

- **不含 Windows / Linux** 本地打包脚本；其他平台仍沿用现有方式。
- **不含 CI/CD 自动化**：本期不将脚本纳入远程构建流水线；若未来扩展，另开变更。
- **不改变打包产物业务语义**：不新增安装包类型、不修改应用功能；仅改善本地出包的操作与校验体验。
- **不涉及用户可见界面**：无 Electron 设置页、无发版管理 UI。

## 功能需求

### 1. 统一本地打包入口

| 编号 | 需求描述 |
|------|----------|
| F1.1 | 在 `scripts/deploy/` 目录下提供 macOS 本地打包入口，开发者执行一次即可启动完整 mac 出包流程。 |
| F1.2 | 打包流程应覆盖与现有 electron-builder mac 目标等价的构建与打包步骤，产出 dmg 等既有形态的安装包。 |
| F1.3 | 最终产物输出至 `release/`，与现有 mac 打包约定一致。 |

### 2. 打包前环境与依赖检查

| 编号 | 需求描述 |
|------|----------|
| F2.1 | 在真正开始构建前，对关键前置条件进行检查；不满足时 **中止打包** 并输出清晰、可操作的失败说明（而非冗长的底层报错堆栈）。 |
| F2.2 | 检查项应至少覆盖以下意图（具体项可在设计阶段按项目现状补全，默认可调整）： |
| | · **运行环境**：Node 版本是否符合项目要求 |
| | · **必要工具**：mac 打包链路依赖的工具/组件是否可用 |
| | · **签名与公证相关**：若项目配置要求代码签名或公证，相关证书、凭据或环境是否就绪；若未配置签名，应明确说明当前为「无签名/跳过」路径而非静默失败 |
| F2.3 | 全部必检项通过后，才进入实际打包；可选检查项失败时行为（警告继续 vs 中止）可在设计阶段定义，PRD 默认倾向 **必检失败即中止**。 |

### 3. 版本号

| 编号 | 需求描述 |
|------|----------|
| F3.1 | **默认**：从项目当前版本信息（package.json 中的版本字段）读取，无需额外参数即可按当前版本出包。 |
| F3.2 | **可选**：支持在触发打包时显式指定版本号，用于预发版、打 tag 前验证等场景。 |
| F3.3 | 指定版本与默认读取版本的行为互斥关系应明确，避免同一轮打包出现版本来源歧义（细则在设计阶段定义）。 |

### 4. 与现有 npm scripts 的关系

| 编号 | 需求描述 |
|------|----------|
| F4.1 | 现有 `dist:mac`、`pack:mac` 等 npm 命令 **保留**，作为开发者熟悉的触发方式。 |
| F4.2 | npm 命令与 deploy 脚本的关系为：**npm 作为薄封装，底层调用 deploy 目录下的统一逻辑**，避免两套独立、可能漂移的打包路径（实现细节不在本文展开）。 |
| F4.3 | 直接调用 deploy 脚本与通过 npm 命令触发，在检查项、版本号行为、产出物上应保持一致。 |

## 范围边界

| 维度 | 范围内 | 范围外 |
|------|--------|--------|
| 平台 | 仅 macOS | Windows、Linux |
| 触发方式 | 开发者本机手动执行 | CI 定时/推送触发 |
| 产出 | dmg 等现有 mac 安装包，输出 `release/` | 新增安装包类型、应用商店提交流程 |
| 脚本位置 | `scripts/deploy/` | 迁移或替换 scripts/ 下既有 bundle/after-pack 等辅助脚本的职责（除非设计阶段证明必须调整） |

## 用户场景

### 场景 A：日常本地验证包

开发者在功能开发完成后，于本机 macOS 执行统一打包入口，脚本自动检查环境与版本，通过后生成与现网一致的 dmg，用于自测安装。

### 场景 B：环境未就绪

开发者首次在本机打包，Node 版本过低或签名证书未配置。脚本在检查阶段即失败，并提示缺失项与建议操作，避免长时间构建后才报错。

### 场景 C：指定版本出包

发版前需验证特定版本号展示与更新逻辑，开发者显式指定版本号触发打包，产出对应该版本的安装包。

### 场景 D：沿用 npm 习惯

开发者继续执行 `npm run dist:mac`（或等价命令），行为与直接调用 deploy 脚本一致，无需学习全新命令体系。

## 验收标准

1. **一键出包**：在 macOS 本机、环境满足前提下，通过 deploy 目录下的统一入口可完成 mac 打包，产出位于 `release/` 的 dmg（含 x64 与 arm64 目标，与现有一致）。
2. **检查生效**：故意制造至少一项必检失败（如 Node 版本不符或缺少必要工具），脚本在构建开始前失败，并给出人类可读的说明，不进入长时间构建。
3. **默认版本**：未指定版本时，产出安装包的版本信息与 package.json 当前版本一致。
4. **指定版本**：显式指定版本时，产出安装包的版本信息与指定值一致。
5. **npm 一致性**：通过 `dist:mac` / `pack:mac`（或项目内等价 npm 命令）触发时，检查、版本与产出行为与直接调用 deploy 入口一致。
6. **范围合规**：不提供 Windows/Linux 打包入口；脚本与文档不暗示 CI 集成为本期交付范围。
7. **无用户界面变更**：Electron 应用界面与安装体验无因本变更而产生的可见变化（仅改善开发者本地出包流程）。
