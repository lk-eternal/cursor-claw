> **来源**：kb-propose
> **类型**：体验优化
> **优先级**：P1
> **外部 PRD**：无
> **Figma 设计图**：无
> **任务记录**：无

## 背景与问题

变更「消息通道即时响应与流式输出」已上线：用户每条消息入队后会收到「已收到，正在处理」及排队条数提示，Agent 处理期间有三态进度与流式输出等能力。

但在**飞书私聊连发多条消息**时，仍存在体验断层：

1. **不知 Agent 在干什么**：入队确认仅告知「已收到」与排队数，未反映 Agent 当前是在处理上一条、仍在启动、还是空闲等待领取。用户连发时容易误以为系统卡住或重复处理。
2. **不知合并结果**：同一会话内多条待处理消息会在 Agent 下次领取时合并为一条再交给 Agent 处理，但**用户看不到合并后的完整内容**，无法在 Agent 开工前核对「最终会发什么给 Agent」。
3. **无法修改合并内容**：若用户发现连发内容有误或想调整表述，目前缺少明确、可引用的修改路径；系统也未提供带唯一标识的合并预览供用户引用。

上述问题在 Agent 正忙、用户快速补充说明的多轮对话中尤为突出，削弱用户对排队与合并机制的信任。

## 目标与非目标

### 目标

1. **入队即告知 Agent 现状**：用户每发一条消息，入队反馈除确认收到外，还应说明 Agent **当前所处状态**（如正在处理、正在启动、排队等待等），让用户理解「为什么还没轮到这条」。
2. **合并前可见预览**：同一会话内、尚未被 Agent 领取的多条消息，在合并完成后、Agent 领取前，向用户展示**合并后的完整预览**，并附带**合并消息 ID**（产品级唯一标识，便于核对与引用）。
3. **可修改合并内容**：用户若需调整合并结果，通过**直接回复合并预览消息**提交新的完整合并正文；系统从被回复的消息关联到对应合并批次，**用户无需在修改内容中手动填写合并消息 ID**。引导文案仍须同时展示**合并消息 ID** 与**合并消息全文**供核对。
4. **与既有反馈协调**：在增强状态与预览能力的同时，避免与三态进度、流式输出、Get 表情等既有通知重复刷屏或语义冲突。

### 非目标

- 本期以**飞书私聊**为主场景；群聊、微信通道列为二期或非目标，除非后续单独立项扩展。
- 不改变消息入队顺序、会话路由、指令拦截等既有业务规则的本质逻辑。
- 不向用户暴露队列文件名、进程信息、内部步骤名等技术细节。
- 不涉及 Electron 设置界面、通道凭据配置等桌面端 UI 改造。
- 不重新定义 Agent 侧合并分隔格式（沿用既有「多条合并为一条、段间用【消息 N】分隔」的产品语义即可）。

## 用户与场景

### 场景 A：Agent 正忙，用户连发补充

用户正在等待 Agent 处理第一条消息，又连续发送 2～3 条补充说明。每条新消息入队时，用户应看到：已收到确认 + **Agent 正在处理上一条**（或等价表述）+ 当前排队位置；当这批待合并消息在 Agent 下次领取前就绪时，用户收到**合并预览**及合并消息 ID。

### 场景 B：Agent 空闲，用户连发多条

Agent 当前无进行中的任务，用户短时间内连发多条。每条入队反馈应体现 **Agent 空闲、消息已排队等待领取**（而非「正在处理」）；合并预览在「下一批待领取消息」确定后、Agent 领取前发出。

### 场景 C：用户查看并确认合并内容

用户收到合并预览，阅读合并后的全文（含各条原文的分段标识）。若内容符合预期，无需操作，等待 Agent 处理即可。

### 场景 D：用户需要修改合并内容

用户发现合并预览有误或想改写。**直接回复该条合并预览消息**，发送希望提交的**完整合并正文**即可；系统从被回复的预览消息关联到对应合并批次，无需用户在正文中手动填写合并消息 ID。预览与引导文案中仍展示合并消息 ID 与合并全文供核对（具体规则见功能需求 F3）。

### 场景 E：单条消息、无合并

用户仅发送一条消息，或上一条已被 Agent 领取后只发一条。不产生合并预览；入队反馈仍须反映 Agent 现状，行为与场景 A/B 的状态规则一致。

## 与已有「入队确认 / 排队提示」的关系

| 既有能力 | 本期关系 |
|----------|----------|
| 入队即时确认（≤3s、「已收到，正在处理」） | **保留**；在此基础上**增强** Agent 现状描述，非替换 |
| 排队条数提示（「前面还有 N 条待处理」） | **保留**；与 Agent 现状文案组合呈现，避免重复两句近义话 |
| 三态进度（已收到 → 处理中 → 完成） | **并存**；入队反馈侧重「本条刚入队时的 Agent 快照」，三态侧重「当前被 Agent 处理的那条任务」的全生命周期 |
| 流式输出 | **协调**；Agent 处理中不向用户重复发送与流式卡片冲突的合并预览或冗余状态 |
| Get 表情 / 正在输入 | **并存**；文本状态为主，原生指示为辅，语义一致 |

原则：**增强而非重复刷屏**——同一次用户动作不触发多条含义重叠的通知；合并预览与修改引导为**新增**节点，不与单条入队确认合并为一条超长消息（除非产品验收另有合并展示约定）。

## 功能需求

### F1 Agent 现状反馈（每条入队时）

用户消息成功写入处理队列后，除确认收到外，须根据**该会话 Agent 当前状态**选择主文案（可与排队提示组合为一条消息）。

| 编号 | Agent 现状 | 用户可见主文案（示例） | 排队提示 |
|------|------------|------------------------|----------|
| F1.1 | 正在处理本会话中的上一条/当前任务 | 「已收到。Agent 正在处理上一条，你的消息已排队」 | 若队列中在本条之前尚有未领取条数，附加「前面还有 N 条待处理」 |
| F1.2 | 正在启动（冷启动，尚未进入处理） | 「已收到。Agent 正在启动，你的消息已排队」 | 同上 |
| F1.3 | 空闲，无进行中的本会话任务，消息等待下次被领取 | 「已收到，等待 Agent 领取」或「已收到，已加入待处理队列」 | 若仅本条一条待领取，可不强调排队数；若已有未领取积压，附加排队提示 |
| F1.4 | 指令拦截、未进入常规队列 | 不适用本需求，沿用既有指令反馈 | — |

补充规则：

- F1.5 每条成功入队的用户消息**单独**发送一次入队反馈，不因连发而省略。
- F1.6 文案须为简体中文、简洁非技术化；**不得**出现工具名、内部状态码、文件名等。
- F1.7 若 Agent 现状与排队数同时存在，**优先保证现状可读**；排队数作为补充，避免两条独立消息。

### F2 合并预览

| 编号 | 需求描述 |
|------|----------|
| F2.1 | **触发时机**：同一会话内存在 **2 条及以上**尚未被 Agent 领取的用户消息，且系统已确定「下一批将被合并领取」的内容时，在 **Agent 领取该批消息之前**，向用户发送一次**合并预览**。 |
| F2.2 | **预览内容**：展示合并后的**完整正文**（各条原文按既有产品语义分段，如【消息 1】【消息 2】…），使用户所见与 Agent 即将收到的内容一致。 |
| F2.3 | **合并消息 ID**：每条合并预览须附带**产品级唯一标识**（下称「合并消息 ID」），格式为 `MG-{profile}-{日期到时分秒}`，其中 profile 为可识别的用户/会话短标识，具体生成规则设计阶段定义；示例：`MG-kiki-20260627153045`。 |
| F2.4 | **单条无预览**：仅 1 条待领取消息时不发送合并预览；用户仅收到 F1 入队反馈。 |
| F2.5 | **预览更新**：用户在预览发出后、Agent 领取前又发送新消息，导致待合并集合变化时，**沿用同一合并消息 ID**，在预览中标注「已更新」并展示最新合并全文，不换新 ID，避免用户依据过期预览修改。 |
| F2.6 | **与领取时序**：Agent 一旦领取该批消息，对应合并预览生命周期结束；后续不再对该批次发送修改引导（除非产品定义领取前窗口已关闭的例外）。 |

### F3 修改合并内容（回复预览消息）

| 编号 | 需求描述 |
|------|----------|
| F3.1 | 合并预览消息中须包含**修改指引**：若需修改合并内容，请**直接回复本条预览消息**，发送新的完整合并正文。 |
| F3.2 | **修改方式（产品约定，可验收）**：用户**回复合并预览消息**（而非在会话中另发独立消息），正文为希望提交的**完整合并全文**（将替代原合并内容交给 Agent）。系统从**被回复的预览消息**关联到对应合并批次，**用户无需在正文中手动填写合并消息 ID**。 |
| F3.3 | **引导文案硬性要求**：任何引导用户修改的提示（含预览内嵌说明、解析失败时的纠错提示），**必须同时包含**「合并消息 ID」与「当前合并消息全文」，不得仅给 ID 或仅给摘要；并说明「回复本条预览消息」的操作方式。 |
| F3.4 | 用户通过回复预览成功提交后，系统以新全文作为该批待领取消息的合并结果；并向用户确认已接受修改（文案见示例表）。 |
| F3.5 | 未回复预览消息、正文为空或无法关联到有效合并批次时，回复可理解的失败说明，并**再次附带**正确的合并消息 ID + 全文 + 操作说明（回复本条预览消息）。 |
| F3.6 | 修改仅作用于**尚未被 Agent 领取**的对应合并批次；已领取或已开始的任务不适用（应提示用户改发新消息或等待当前任务结束）。 |

### F4 与三态进度 / 流式输出的协调

| 编号 | 需求描述 |
|------|----------|
| F4.1 | Agent **正在处理**某条任务且已处于「处理中」或流式输出阶段时，**不再**向用户发送新的合并预览（新消息仅 F1 入队反馈 + 排队信息，预览留待当前任务结束、下一批待领取消息就绪后再发）。 |
| F4.2 | 入队反馈（F1）与三态进度（处理中 / 流式）**语义分工明确**：入队反馈回答「我刚发的这条怎样了」；三态与流式回答「Agent 正在处理的那条进展如何」。避免同一时刻两条「Agent 处理中」类重复通知。 |
| F4.3 | 流式卡片更新期间，不插入合并预览或修改引导消息，以免打断阅读；预览与修改引导走**独立消息**通道。 |
| F4.4 | 任务完成或失败后，停止进行中指示的规则沿用既有变更，本期不弱化。 |

## 文案示例表

### 入队反馈（F1）

| 情况 | 示例文案 |
|------|----------|
| Agent 忙 + 有排队 | 「已收到。Agent 正在处理上一条，你的消息已排队（前面还有 2 条待处理）。」 |
| 冷启动 + 有排队 | 「已收到。Agent 正在启动，你的消息已排队（前面还有 1 条待处理）。」 |
| Agent 空闲 + 仅本条 | 「已收到，等待 Agent 领取。」 |
| Agent 空闲 + 已有积压 | 「已收到，已加入待处理队列（前面还有 1 条待处理）。」 |

### 合并预览（F2 + F3 引导）

```
【合并预览 · ID：MG-kiki-20260627153045】
以下内容将合并为一条发给 Agent：

【消息 1】
请帮我查一下 cursor-claw 的打包脚本

【消息 2】
顺便看看 macOS 本地能不能跑

如需修改，请直接回复本条消息，发送你希望提交的完整合并正文。
```

### 预览更新（F2.5）

```
【合并预览 · ID：MG-kiki-20260627153045 · 已更新】
以下内容将合并为一条发给 Agent：

【消息 1】
……
【消息 4】
……

如需修改，请直接回复本条消息，发送你希望提交的完整合并正文。
```

### 修改成功 / 失败

| 情况 | 示例文案 |
|------|----------|
| 修改成功 | 「已按你的内容更新合并预览（ID：MG-kiki-20260627153045）。Agent 领取后将按新内容处理。」 |
| 未回复预览 / 无法识别 | 「未能识别修改。请直接回复合并预览消息，并发送完整合并正文。当前合并 ID：MG-kiki-20260627153045；当前全文：……（完整粘贴）……」 |
| 已领取不可改 | 「该批消息 Agent 已开始处理，无法修改。如需补充请直接发送新消息。」 |

## 非功能需求

| 编号 | 描述 |
|------|------|
| NF1 | 入队反馈（含 Agent 现状）延迟：与既有 SLA 一致，P95 ≤ 3 秒，P99 ≤ 5 秒。 |
| NF2 | 合并预览须在「待合并集合确定且 Agent 尚未领取」后的合理时间内送达，P95 ≤ 5 秒（从最后一条纳入该批的消息入队完成起算，或从集合变更稳定后起算，设计阶段细化）。 |
| NF3 | 合并消息 ID 在同一会话、同一待领取批次内唯一；格式含 profile 与精确到秒的时间戳，全局碰撞概率可忽略（具体生成规则设计阶段定义，产品要求用户可核对、可复制）。 |
| NF4 | 文案统一简体中文；合并预览与修改引导**不得截断**全文（超长时分条或折叠策略设计阶段定义，产品要求用户能核对完整内容）。 |
| NF5 | 连发 5 条消息：每条均有 F1 反馈；至少 1 次合并预览且 ID 与全文正确；全程无重复、矛盾的 Agent 状态描述。 |
| NF6 | 与三态、流式并存时，同一会话在 Agent 处理中单次连发不应出现 3 条以上含义重叠的「处理中」类通知。 |

## 验收标准

1. **Agent 现状 — 处理中**：飞书私聊，Agent 正在处理任务 A 时用户连发消息 B、C；B、C 的入队反馈**均明确**体现 Agent 正在处理上一条（或等价表述），且排队数正确。
2. **Agent 现状 — 空闲**：Agent 空闲时连发 2 条；入队反馈体现等待领取，**不**误报「正在处理上一条」。
3. **Agent 现状 — 冷启动**：Agent 未运行时发送消息；入队反馈体现正在启动 + 已排队，与既有冷启动三态不矛盾。
4. **合并预览触发**：同会话连发 3 条且均未领取时，用户在 Agent 领取前收到 **1 次**合并预览，正文含【消息 1】～【消息 3】及与 Agent 将收到内容一致的完整文本。
5. **合并消息 ID**：预览中 **可见、可复制** 的合并消息 ID，格式为 `MG-{profile}-{日期到时分秒}`；同一预览批次 ID 与引导、修改确认中 ID **一致**。
6. **回复预览修改成功**：用户**回复合并预览消息**并发送新全文后，系统确认修改成功；Agent 领取后处理的是**新全文**（可通过对话结果或验收脚本判定）。
7. **修改引导完整性**：预览及任意修改失败提示中，**同时包含**合并消息 ID 与合并全文，并说明「回复本条预览消息」的操作方式，缺一项即不通过。
8. **修改失败提示**：未回复预览或正文无效时，收到纠错提示且仍含 ID + 全文 + 操作说明。
9. **单条无预览**：仅发 1 条消息时**无**合并预览，仅有 F1 入队反馈。
10. **与流式/三态协调**：Agent 流式输出进行中，用户再发消息：仅 F1 反馈，**不插入**合并预览；无第二条「Agent 处理中」重复刷屏。
11. **预览更新**：预览发出后再发第 4 条，预览**沿用同一 ID** 并标注「已更新」，反映 4 条合并内容；用户不会仅看到旧 3 条预览而无说明。
12. **本期边界**：微信、群聊**不要求**验收合并预览与回复修改；若仅实现飞书私聊，验收报告标注通过范围。
