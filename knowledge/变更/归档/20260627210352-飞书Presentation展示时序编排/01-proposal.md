## 背景与问题

变更「飞书作为 Cursor 展示与控制层」已归档：主用户私聊 SDK 路径已启用统一 Presentation Pipeline，流式正文与工具/思考进度均可经 CardKit 呈现，且同一任务内**不冲突刷屏**。

2026-06-27 联调反馈暴露**展示顺序**问题：当 Agent 执行带工具调用的任务（如「git pull 最新代码」）时，飞书会话中的卡片顺序与用户心智相反——

- **流式正文卡**（assistant 回答）先出现在会话**上方**，并持续更新为完整结论；
- **工具进度卡、思考摘要卡**作为**新消息**出现在**下方**；
- 用户滚动阅读时，视觉上像「Agent 已经完整回复了，工具调用才发生在后面」。

这与对话式 AI 的普遍预期不符：**过程在上、结论在下**。用户应先在上方看到「正在做什么」（思考、工具执行），滚动到底部才看到**最终完整回答**。

### 与已归档变更的边界

已归档变更的 MVP 验收项 2 仅要求「工具进度与流式正文不冲突刷屏」，**未**要求「结论卡片位于过程卡片之下」。本变更专门补齐**时序编排**这一体验缺口。

## 用户心智与场景

### 用户心智

用户在飞书与 Agent 对话时，默认按**时间顺序自上而下**阅读：

1. 先看到**过程**：思考摘要、工具开始/进行中/完成等进度；
2. 最后看到**结论**：assistant 的最终完整回答。

若结论出现在过程之上，用户会误判任务已完成、工具是「事后补充」，削弱对 Agent 执行透明度的信任。

### 场景 A：单条私聊、带工具调用（主复现场景）

主用户通过飞书私聊发送「git pull 最新代码」等需调用 shell/文件类工具的任务。SDK 路径 + CardKit 流式已启用。

**现状**：模型常在调用工具前输出简短 preamble（assistant 开场白），该内容触发流式正文卡并置顶；随后工具卡、思考卡作为新消息出现在下方；正文卡持续 PATCH 直至完整回答。

**期望**：同一会话内，工具/思考类过程卡片**整体位于** assistant 最终回答卡片**之上**；用户滚到底才看到完整结论。

### 场景 B：纯对话、无工具

用户发送无需工具的普通问答（如概念解释、短回复）。

**期望**：流式体验**不劣化**——首段内容仍应在合理时间内可见，不因「等工具结束再展示」策略而引入明显空窗。

### 场景 C：多工具串行或并行

一次 Run 内连续或并行多个工具（如读文件 → 执行命令 → 再读结果）。

**期望**：各工具/思考卡片顺序稳定、语义清晰，**不重复刷屏**；最终回答仍位于全部过程卡片之下。

### 场景 D：合并批次（MergeBatch）

用户连发多条消息触发合并预览与合并 CardKit；过程卡片与 NF2 规定的 reply 策略协同。

**期望**：本变更**不回归**合并批次的 reply 锚定、预览编辑与排队反馈行为；时序规则在合并场景下仍成立。

## 目标与非目标

### 目标

1. **过程在上、结论在下**：含 tool/thinking 的单轮 SDK 私聊中，飞书会话内过程类卡片整体位于 assistant 最终回答之上。
2. **保留多卡 + 流式**：不牺牲 CardKit 流式更新能力；结论仍可在单卡内流式增长，但**创建时机**须服从时序规则。
3. **无 tool 路径不劣化**：纯对话场景的首段可见延迟与现网协调，不明显变差。
4. **多工具稳定**：串行/并行工具顺序可预期，避免重复通知。
5. **可回滚、可观测**：分阶段或 feature 开关控制；顺序违规可日志归因。

### 非目标

- 本期**不**定义具体模块、接口或代码结构（归属 `/kb-design`）。
- **不**在本 propose 阶段修改业务代码或 Agent 规则正文。
- **群聊、CLI** 通道的时序编排列为**阶段 2**；MVP 验收范围为主用户**私聊 SDK**。
- **不**重做 CardKit 视觉样式或控制层卡片（停止、新话题等）。
- **不**改变消息入队、合并语义、工具批准等业务规则本质。

## 方案对比

以下方案均为**产品向**选项，技术落点由 design 阶段细化。

### 方案 A：延迟 assistant 卡片创建（推荐倾向）

**思路**：在存在**进行中**的工具或思考展示时，**暂不创建** assistant 流式正文卡；过程卡片先发；待全部过程结束（或进入「仅输出结论」阶段）后，再创建 assistant 卡并流式更新，使其自然落在会话最下方。

| 维度 | 说明 |
|------|------|
| **用户体验** | 最贴近「过程在上、结论在下」；用户先读工具/思考，滚到底见结论；纯对话无 tool 时与现网接近（无等待窗口）。 |
| **飞书 CardKit 约束** | 仍为多消息多卡；依赖消息创建时间排序；需产品规则定义「进行中 tool/thinking」边界，避免 assistant 永久不出现。 |
| **实现复杂度** | **中** — 需在 Presentation 层统一编排「何时首建 assistant 卡」，协调流式 delta 缓冲与过程事件。 |
| **风险** | 若边界判定不准，可能延迟纯 preamble 展示；需与 NF2 首段可见 SLA 协调；长 tool 期间用户可能暂无任何 assistant 文字（可接受若过程卡清晰）。 |

### 方案 B：单卡多区块（过程区 + 结论区）

**思路**：同一 CardKit 卡片内划分**过程区块**（tool/thinking）与**结论区块**（assistant），过程更新在上、结论流式更新在下，对外仅一条消息。

| 维度 | 说明 |
|------|------|
| **用户体验** | 顺序天然正确；单条消息内上下分区，阅读路径清晰。 |
| **飞书 CardKit 约束** | 依赖 CardKit 是否支持**同卡多区块独立 PATCH** 及区块顺序稳定；若 API 仅支持整卡替换或单一流式区，可能受限。 |
| **实现复杂度** | **高** — 卡片 schema、流式 PATCH 粒度、过程与结论并发更新均需新约定；与现有「多卡出站」架构差异大。 |
| **风险** | CardKit 能力不满足时需降级；单卡体积过大影响渲染；与 MergeBatch 多卡模型可能冲突。 |

### 方案 C：Run 结束后再发最终回答

**思路**：过程阶段仅展示 tool/thinking 卡；assistant 产出在服务端**缓冲**，Run 完全结束后再一次性或流式发出最终回答卡。

| 维度 | 说明 |
|------|------|
| **用户体验** | 顺序正确；但 tool 期间**完全看不到** assistant 任何文字（含 preamble），等待感可能更强；结论失去「边生成边可见」的流式感，除非结束后仍走 CardKit 流式。 |
| **飞书 CardKit 约束** | 多卡顺序易控；结束后单卡流式仍可用 CardKit。 |
| **实现复杂度** | **中** — 需缓冲全文与过程事件解耦；Run 异常中断时须定义部分结论是否展示。 |
| **风险** | 与已建立的「流式首段可见」产品预期冲突较大；长回答结束后才开始流式，首字延迟 = 全 Run 时长，体验回退明显。 |

### 方案 D：Reply 链 / Thread 锚定

**思路**：过程卡仍按现有方式先发；assistant 流式卡通过**回复**最后一张过程卡（或 thread 根）发出，利用飞书 reply 在 UI 上形成「挂在过程下方」的视觉效果。

| 维度 | 说明 |
|------|------|
| **用户体验** | 在支持 thread/reply 折叠的客户端上可能接近预期；不同客户端展示不一致时顺序感仍可能混乱。 |
| **飞书 CardKit 约束** | 依赖私聊 reply API 与 CardKit 流式卡 reply 兼容性；MergeBatch 已有 reply 锚定逻辑，需避免与普通单条路径规则打架。 |
| **实现复杂度** | **中** — 需统一 reply 锚点策略（最后 tool 卡 vs 用户消息 vs 合并卡）；与 NF2、MergeBatch 策略交叉。 |
| **风险** | 飞书排序仍以 message 创建时间为准时，reply 仅视觉嵌套、列表顺序仍可能置顶 assistant；多端表现不一致。 |

### 推荐倾向

**优先方案 A（延迟 assistant 卡片创建直至无进行中 tool/thinking）**，理由：

1. 直接对齐用户心智，且**保留多卡 + CardKit 流式**架构，与已归档 Presentation Pipeline 延续性好。
2. 相对方案 B 不依赖 CardKit 多区块未知能力；相对方案 C 不牺牲 tool 场景外的流式首段体验；相对方案 D 不依赖客户端 reply 展示差异。
3. 方案 B/C/D 可作为 design 阶段 fallback 或分场景补充，但 MVP 应以 A 为主路径验收。

## 功能需求（产品级）

| 编号 | 需求描述 |
|------|----------|
| F1 | 含 tool 或 thinking 的单轮任务：Presentation 须保证**过程类卡片**（工具进度、思考摘要等）在飞书会话时间轴上**整体先于** assistant 最终回答卡片出现。 |
| F2 | assistant 最终回答仍支持 CardKit **流式更新**；时序规则针对**首条 assistant 卡片的创建时机**，而非禁止流式。 |
| F3 | 无 tool/thinking 的纯对话：assistant 流式卡片创建策略与现网一致或等价，**不引入**额外可感知空窗。 |
| F4 | 多 tool 串行/并行：过程卡片按发生顺序展示，**不重复**发送语义重叠的多张过程卡。 |
| F5 | MergeBatch 活跃期间：与既有 reply 策略、合并预览、NF2 不冲突；时序规则在合并批次内仍满足 F1（或在 design 明确合并场景等价验收）。 |
| F6 | 提供**可配置开关**（或分阶段放量），可在顺序编排异常时回退至现网「先到先展示」行为。 |

## 验收标准

1. **含 tool 的单轮 SDK 私聊**：至少 3 次实测（含「git pull 最新代码」或等价 shell 工具任务），飞书会话中 **tool/thinking 卡片整体位于 assistant 最终回答卡片之上**；用户需**滚动到底**才看到完整结论；过程与结论**无**时间轴倒置。
2. **无 tool 纯对话**：至少 10 次短问答实测，首段内容可见延迟 **P95 ≤ 3 秒**，或**不明显劣于**现网同场景（与变更「消息通道即时响应与流式输出」NF2 协调）；流式更新流畅、不刷屏。
3. **多 tool 串行/并行**：至少 2 次多步工具任务，过程卡片顺序稳定、**无**重复刷屏或同一工具多次「开始/完成」语义重叠通知。
4. **MergeBatch 不回归**：连发触发合并批次的场景下，合并预览、reply 锚定、排队反馈行为与归档变更一致；时序验收至少 1 次通过或 design 明确标注合并场景等价用例。
5. **异常与中断**：工具失败或 Run 中止时，用户仍能看到已发生的过程卡片与可理解的结论/失败说明，**不出现**「仅有结论、过程缺失」或顺序错乱。
6. **回滚验证**：关闭 feature 开关后，行为恢复为变更前「先到先展示」，无残留编排状态导致卡死或重复发 card。

## 非功能需求

| 编号 | 描述 |
|------|------|
| NF1 | **可观测性**：当检测到「assistant 卡早于过程卡创建」等顺序违规时，须写入可检索日志（含 run/会话标识、事件类型、卡片创建顺序），便于联调归因。 |
| NF2 | **可回滚**：时序编排须支持 feature 开关或分阶段配置；默认 MVP 仅作用于主用户私聊 SDK，避免误伤群聊/CLI。 |
| NF3 | **与 NF2 协调**：纯对话首段可见与「消息通道即时响应与流式输出」既有 SLA 协调；含 tool 场景允许 conclusion 首段延迟至过程结束，但须在验收 1 中明示可接受。 |
| NF4 | **幂等与稳定**：同 Run 内重复事件或重试**不**导致 assistant 卡重复创建或过程卡重复刷屏。 |
| NF5 | **文案与语义**：过程卡与结论卡仍不向用户暴露内部模块名；与三态进度、入队确认等既有通知**不**语义重叠刷屏。 |

## 范围外

- **群聊、CLI** 通道的 Presentation 时序编排（阶段 2 单独立项或随 Presentation 放量扩展）。
- CardKit 视觉 redesign、控制层按钮（停止、新话题等）。
- 改变 Agent 推理顺序或禁止模型输出 tool 前 preamble（属模型行为，本产品通过**展示编排**解决）。
- 微信等非飞书通道。

## 待确认项

1. **进行中 tool 的判定边界**：thinking 是否一律视为过程、assistant preamble 是否一律延迟，design 阶段结合飞书 CardKit 与 SDK 事件语义细化。
2. **纯对话误延迟**：无 tool 但模型输出较长「思考型」正文时，是否触发延迟策略，需 design 给出产品规则。
3. **阶段 2 放量范围**：群聊/CLI 是否沿用同一编排规则，或保持现网行为直至单独验收。
