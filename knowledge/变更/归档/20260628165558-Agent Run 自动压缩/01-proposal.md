## 背景

用户通过飞书等即时通讯通道与 Agent 连续对话。同一 IM 会话内，用户可能在短时间内连续发送多条消息（例如同一上午连续三次追问或补充需求）。随着多轮 Run 累积，会话上下文持续膨胀；当第三次 Run 失败时，用户往往只能看到 **「⚠️ Agent 处理失败，请稍后重试。」** 一类通用文案，**无法判断** 是上下文已满、执行超时、会话异常，还是其它原因，因而不知道下一步该精简输入、等待压缩完成，还是重新发消息。

**与既有能力的关系（非从零建设）**：

已归档变更「Agent 自动压缩与上下文占用展示」已交付：执行引擎 harness 默认接近上限自动 summarization/compression、回复末尾上下文占用 footer、SDK UI 日志 `[compression]` 前缀、压缩开始时飞书通知「正在压缩上下文…」。后续「上下文占用统计修复」修正了 footer 统计口径。

本变更定位为 **在 Run 生命周期内增强自动压缩的可靠性与可感知性，并补齐失败原因的可读性**，解决「压缩未及时生效或用户无感知 → Run 仍失败 → 失败原因不可理解」的体验缺口，**不**重复 footer 展示或从零定义压缩机制。

## 目标与非目标

### 目标

1. **Run 期间可靠自动压缩**：在同一 IM 会话连续多轮发消息、上下文持续累积时，系统应在 Run 触及不可继续的上限 **之前** 自动触发压缩，使 Run 尽可能 **正常完成** 而非直接失败。
2. **压缩过程用户可感知**：压缩进行中，用户经 IM 通道能明确感知「系统正在压缩上下文」（与「Agent 处理中…」区分或衔接），避免长时间静默后突然失败。
3. **失败原因可读**：当 Run 仍因上下文、超时、会话异常等原因失败时，用户可见文案须给出 **可理解的失败类别与下一步建议**（例如上下文已满、请精简后重发；会话已结束、请重新发送消息），**不得** 在可归因场景下仅显示「请稍后重试」。
4. **压缩后继续**：压缩成功完成后，当前 Run 应能继续执行并产出回复（或明确的非压缩类失败），用户无需手动 Stop/Reset。

### 非目标

- **不** 重新定义或调整回复末尾 **上下文占用 footer** 的格式、统计口径与展示路径（见关联变更「上下文占用统计修复」）。
- **不** 重新定义 Run **超时阈值** 或保活策略；超时发生时的自动停止与会话恢复见关联变更「Agent Run 超时自动停止」，本 PRD **不重复** 其验收项。
- **不** 新增设置页、仪表盘或 Figma 视觉改版；压缩与失败信息经既有 IM 消息形态传达即可。
- **不** 在本 PRD 中规定具体模块、接口或日志字段（归属 `/kb-design`）。
- **SDK MCP stdio 相对路径**：与上下文压缩无直接因果关系；若工具因路径问题导致 Run 失败，属独立议题（见关联变更「SDK MCP stdio 相对路径支持」），**不在** 本变更必达范围；design 阶段仅评估是否与失败文案归因交叉。

## 用户与场景

### 目标用户

- **IM 日常用户**：通过飞书等与 Agent 连续追问，期望多轮对话稳定、失败时能看懂原因。
- **长任务使用者**：单条或多条消息触发大量工具调用与中间结果，更容易在第三次及以后 Run 触及上下文边界。

### 场景 A：连续多轮发消息，第三次 Run 失败（核心痛点）

用户在同一会话内连续发送三条消息（或三次追问）。前两轮可能正常回复；第三轮 Agent 开始处理后出现失败 notify，文案仅为「Agent 处理失败，请稍后重试」，用户 **不知道** 是否与上下文过长有关，也不清楚是否应换话题或等待。**期望**：系统在第三轮 Run 过程中 **主动压缩** 并尽量完成回复；若仍失败，文案说明 **上下文相关或其它可归因原因** 及建议操作。

### 场景 B：压缩进行中用户可感知

Run 执行过程中上下文接近上限，系统开始自动压缩。用户期望在 IM 通道看到 **明确进行中状态**（例如「正在压缩上下文…」或与处理中状态的合理衔接），而非长时间无反馈后突然失败。**期望**：压缩开始至完成期间，用户能感知系统仍在处理；压缩完成后 Run 继续。

### 场景 C：压缩后 Run 继续并成功回复

接场景 B，压缩完成后 Agent 继续本轮任务并产出最终回复。用户期望 **无需** 再次发送相同消息或手动 Stop/Reset，且终态回复仍附带既有上下文占用 footer（footer 行为本身不在本 PRD 重新定义范围内）。

### 场景 D：压缩无法挽救时的明确失败说明

上下文已无法通过压缩继续（或压缩后仍超限、或发生非压缩类致命错误）。用户期望收到 **一条** 简体中文说明，语义包含：**失败类别**（如上下文已满、执行超时、会话异常等可理解表述）、**建议下一步**（如精简需求后重发、直接重新发送消息继续），**不得** 仅「请稍后重试」。若失败与超时自动停止相关，文案应与超时类友好提示 **可区分或互补**，且不重复「Agent Run 超时自动停止」已定义的验收路径。

## 功能需求

### F1 Run 生命周期内自动压缩触发

- 在同一 IM 会话 **连续多轮 Run**（用户多次发消息、每次触发新 Run 或延续会话）场景下，系统须 **主动** 在上下文危及 Run 继续之前触发自动压缩，而非仅依赖单次 Run 内被动触发。
- 自动压缩行为须与 Cursor 产品侧 summarization/compression **语义一致**；用户 **无需** 手动执行斜杠命令或额外配置。
- 压缩触发与 Run 调度、会话 idle/processing 状态 **协调一致**：不得因压缩过程导致会话长期卡在不可发新消息的状态（与超时自动停止变更互补，不重复其 F1/F2 验收）。

### F2 压缩过程 IM 可感知

- 压缩 **开始** 时，经 IM 通道向用户下发 **可理解的进行中提示**（可与既有「正在压缩上下文…」衔接或增强，但须让用户明确当前处于 **压缩阶段**，而非普通「处理中」）。
- 同一 Run 内对用户的压缩进行中提示 **不得** 重复骚扰（例如多次相同通知）；压缩 **完成** 后不得再追加同义进行中提示。
- 压缩进行中 **不得** 向用户下发技术堆栈、内部错误码或原始平台报错。

### F3 失败原因可读性

- 当 Run 失败且经 IM notify 用户时，若失败 **可归因** 为下列之一或等价类别，用户可见文案须 **明确体现类别与建议**，不得退化为仅「Agent 处理失败，请稍后重试」：
  - **上下文已满 / 压缩后仍无法继续**（建议精简输入或开启新话题）；
  - **执行超时**（建议重新发送消息；与超时自动停止变更的专用文案 **不冲突**，本项侧重 **非超时路径或并存时的归因完整性**）；
  - **会话异常 / 需重新发起**（建议重新发送消息，无需 Stop+Reset 的表述与超时恢复一致）；
  - **其它可安全展示的产品级原因**（当底层 message 不可读时，仍须映射到上述类别之一，而非通用重试）。
- 路径、stack、进程细节 **仅** 写入开发者/UI 日志， **不得** 经 IM 下发。
- 同一失败事件 **不超过一条** 用户可见失败 notify（与超时变更 F3 防护一致）。

### F4 与既有 footer 及 UI 日志的兼容

- 压缩与失败文案增强 **不得** 破坏既有：终态回复末尾上下文 footer、错误 notify 在占用数据可得时的 optional footer、SDK UI 日志 `[compression]` / `[context-usage]` 可观测性。
- 本 PRD **不要求** 新增独立 CardKit 类型或 Electron 设置项。

## 验收标准

1. **连续多轮 Run**：在同一会话内连续发送至少 **三次** 用户消息（可含工具密集型任务），第三次 Run **优先** 通过自动压缩 **正常完成并回复**；若仍失败，用户可见文案 **不是** 仅「请稍后重试」，且能体现 **可归因失败类别** 与建议（对应场景 A、F3）。
2. **压缩触发可观测**：在上述或模拟接近上限场景中，可观察到自动压缩 **在 Run 失败前** 发生（SDK UI 日志 `[compression]` 或等价记录；IM 进行中提示见下条）。
3. **IM 压缩感知**：压缩开始时，用户 IM 通道收到 **明确的压缩进行中提示**（语义含「正在压缩上下文」或等价表述），且 **同一 Run 至多一条** 该类进行中 notify（对应场景 B、F2）。
4. **压缩后继续**：压缩完成后，当前 Run **继续执行** 并产出终态回复或明确的非压缩类失败；用户 **无需** Stop+Reset 即可在同会话发送下一条消息（对应场景 C、F1）。
5. **上下文耗尽类失败**：在可复现的「压缩无法继续 / 上下文已满」场景下，失败 notify 明确说明 **上下文相关** 原因并建议精简或新话题，**不得** 仅通用重试文案（对应场景 D、F3）。
6. **不可读底层 message**：当 SDK 返回不可安全展示的技术 message 时，仍须映射为 **可理解类别**（上下文、超时、会话异常等之一），**不得** 回退为唯一通用句（对应 F3、用户原话痛点）。
7. **无回归**：既有 footer 展示、占用统计修复后的 footer 数值合理性、`[compression]` UI 日志 **不退化**；超时自动停止与主动 Stop 路径 **无行为回归**（抽样回归即可）。
8. **通道防护**：失败与压缩相关 IM 文案 **不含** stack、路径、内部 error 对象；同一失败事件 **不超过一条** notify。
