> **来源**：kb-propose
> **类型**：稳定性
> **优先级**：P1
> **外部 PRD**：无
> **Figma 设计图**：无

## 背景与问题

cursor-claw 主用户私聊等场景采用 **Cursor SDK 本地 Run** 驱动 Agent，会话保活依赖 Agent 在任务完成后进入「阶段 4 保活轮询」，通过 Shell 调用 `GET /api/poll-message` **阻塞挂起**等待下一条用户消息。Daemon 侧对阻塞 poll 设有 **25 分钟**超时，超时后返回 SYSTEM OVERRIDE 占位指令，驱动 Agent 继续下一轮 poll，以避免 Run 在无用户输入时过早结束。

近期诊断发现：SDK Run 在保活阶段被 **SDK 平台以 `status=error` 终止**，用户侧收到失败通知，但 **缺少可还原根因的结构化信息**；且该失败与飞书通道收发、排队合并等能力 **无直接因果**。

### 诊断结论（须纳入本变更背景）

| 项 | 结论 |
|----|------|
| 典型失败 Run | `run-4dac4a72` |
| 运行时长 | `durationMs=1395228`（约 **23.2 分钟**） |
| 关联通道/会话 | `ch_0b1b964e` |
| 终态特征 | `status=error`，**无** `message` / `result` 等可读原因 |
| 末次工具事件 | 历史 **5 次** ERROR Run 的末条 tool 事件均为 **`shell:running`**（即仍卡在阻塞 poll 的 Shell 调用上） |
| 超时档位 | 观测到约 **23 分钟**与约 **60 分钟**两档 Run 被终止的模式 |
| Daemon 25min 超时 | **未触发**——Agent 侧 Shell 仍在阻塞等待 poll 响应时，Run 已先被 SDK 终止 |
| 与飞书通道 | **无直接因果**；问题出在 SDK Run 生命周期与本地保活策略的兼容性 |

### 用户可见症状

1. Agent 在完成一轮回复并进入「等待下一条消息」后，用户在 **未发新消息** 的情况下收到 **「Agent 处理失败，请稍后重试」** 类通用失败文案。
2. 开发者从 UI 日志难以区分：**SDK 平台超时终止**、**保活 Shell 长时间阻塞**、还是 **其它工具/网络故障**。
3. Run 非正常结束后，会话需用户 **重新发消息** 才能恢复，长连接式「随时可发下一条」的体验中断。

### 根因方向（产品级，待设计阶段细化）

- **SDK 侧 Run 生命周期**对「单条 Shell 长时间 blocking（long-poll）」的容忍度有限，可能在 Daemon 25 分钟兜底 **之前** 即以 `error` 结束 Run。
- **错误可观测性不足**：终态仅有 `status=error`，`run.result`、stream 中 `errorCode`、末次 tool 名/状态等未系统沉淀到日志与用户通知链路。
- **保活规则**（`cursor-claw.mdc`）要求 **无限挂起** 的单次 blocking poll，与 SDK Run 实际生命周期 **不匹配**。

## 目标与非目标

### 目标

1. **增强 SDK 错误可观测性**：Run 以 `error` 结束时，运维与开发者能从日志还原 **run.result**、stream 中的 **errorCode**、**末次 tool 名称与状态** 等关键字段，便于归因与复现。
2. **保活策略与 Run 生命周期兼容**：评估并落地「**非阻塞 poll + 短间隔循环**」等替代方案，避免单次 Shell 阻塞接近或超过 SDK 容忍窗口；必要时同步调整 Agent 规则（`cursor-claw.mdc`）与 Daemon/Agent 侧配合行为。
3. **用户可见失败文案可区分**：向用户明确区分 **SDK Run 超时/保活失败** 与 **通用「请稍后重试」**；保活类失败应给出 **可理解、可行动** 的说明（如「会话等待超时，请重新发送消息继续」），而非一律模糊重试提示。

### 非目标

- 不修改飞书/微信 **消息收发、排队、合并预览、流式输出** 等产品语义（除非设计阶段证明与保活时序存在硬耦合）。
- 不改变 **poll-message 必须带 sessionKey**、消息领取/确认等核心队列契约的本质。
- 不引入 **新的用户设置项** 或 Electron 设置页改造。
- 不承诺 **消除 SDK 平台侧全部超时**——本变更聚焦 **兼容其生命周期** 与 **失败可观测、可理解**。
- 本期 **不写** 02-design、不改业务代码（propose 阶段边界）。

## 用户与场景

### 场景 A：任务完成后长时间等待下一条消息

用户通过飞书私聊与 Agent 完成一轮对话；Agent 已回复并进入保活等待。用户 **20～30 分钟内未发新消息**。预期：Run **保持可用** 或 **优雅结束且用户知情**；不应无声失败后再收到含糊的「请稍后重试」。

### 场景 B：保活期间 Run 被 SDK 终止

与场景 A 相同，但 SDK 在约 23 或 60 分钟档位终止 Run。预期：用户收到 **明确属于「等待超时/保活失败」** 的文案；开发者日志含 **末次 tool=shell、duration、errorCode/result** 等字段。

### 场景 C：非保活类真实处理失败

Agent 在执行搜索、改代码、send-text 等 **非 blocking poll** 工具时失败。预期：仍走既有失败路径；**不与** 保活超时文案混淆；可观测性增强同样适用。

### 场景 D：Daemon 25 分钟 SYSTEM OVERRIDE 仍生效

采用非阻塞短循环保活后，若长时间无用户消息，Daemon 仍可按既有策略返回 SYSTEM OVERRIDE，Agent **继续保活循环**而不结束 Run（设计阶段验证与 SDK 新策略的叠加行为）。

## 功能需求

### F1 增强 SDK 错误可观测性

| 编号 | 需求描述 |
|------|----------|
| F1.1 | Run 终态为 `error` 时，**必须**在 UI/开发者日志中记录 `run.result`（若有）。 |
| F1.2 | 解析并记录 stream 终态或 status 事件中的 **errorCode**（若 SDK 暴露）。 |
| F1.3 | 记录 **末次 tool 调用名称与状态**（诊断已表明 ERROR 末条多为 `shell:running`）。 |
| F1.4 | 上述字段 **不得** 原样下发给终端用户；用户侧仍遵循「可理解文案、技术细节仅日志」的既有约定。 |
| F1.5 | 可关联会话标识（如 `sessionKey`、Run id 短码）便于与历史案例（如 `run-4dac4a72`）对照排查。 |

### F2 保活策略与 Run 生命周期兼容

| 编号 | 需求描述 |
|------|----------|
| F2.1 | **评估** 当前「单次 blocking poll 无限挂起」与 SDK Run 超时档位（约 23min / 60min）的冲突，并在设计阶段给出 **推荐保活模式**（预期方向：**非阻塞 poll + 短间隔循环**）。 |
| F2.2 | 更新 Agent 规则 **`cursor-claw.mdc`** 中「阶段 4 保活轮询」的产品语义：从「单次 curl 无限挂起」调整为与新策略一致的 **可验收行为描述**（具体参数如轮询间隔、是否保留 SYSTEM OVERRIDE 衔接，设计阶段定义）。 |
| F2.3 | 若 Daemon **`/api/poll-message`** 或 Agent 启动/调度层需要配合（如默认 `wait=false`、最大单次等待上限、与 SYSTEM OVERRIDE 的衔接），变更范围须在设计阶段列明；**不改变** sessionKey 必填与消息领取语义。 |
| F2.4 | 新保活策略下，Agent 在「等待用户下一条消息」期间 **不应** 因单次 Shell 阻塞时长 alone 触发 SDK `status=error`（以验收可复现为准）。 |
| F2.5 | 保留「仅 Shell 调用 poll、禁止在保活阶段直接输出自然语言」等 **核心禁令** 的产品意图；调整的是 **挂起形态**，不是放松 Loop 协议。 |

### F3 用户可见失败文案区分

| 编号 | 需求描述 |
|------|----------|
| F3.1 | 当失败可归因为 **SDK Run 超时或保活阶段终止**（含末次 tool 为 blocking poll / shell running 且无其它业务 tool 失败）时，用户可见文案 **不得** 仅显示「Agent 处理失败，请稍后重试」。 |
| F3.2 | 保活/Run 超时类文案须 **简体中文**、说明「等待下一条消息时会话已结束」类语义，并引导用户 **重新发送消息** 继续（示例见下表）。 |
| F3.3 | **CANCELLED**、**EXPIRED** 等既有 status 分支 **保留** 现有专用文案，不与 F3.2 混淆。 |
| F3.4 | 通用处理失败（工具异常、网络、通道不可用等）仍可使用「请稍后重试」类表述，但应 **与 F3.2 互斥**——同一失败不应同时满足两种分类。 |
| F3.5 | 用户主动停止 Agent **不** 走失败 notify（沿用既有行为）。 |

### 文案示例（F3）

| 情况 | 示例文案 |
|------|----------|
| 保活/Run 等待超时 | 「会话在等待下一条消息时已结束（等待超时）。请重新发送消息，我会继续为你处理。」 |
| 通用处理失败 | 「Agent 处理失败，请稍后重试。」（沿用既有） |
| 用户取消 | 「Agent 任务已取消。」（沿用既有） |
| 会话过期 | 「Agent 会话已过期，请重新发送消息。」（沿用既有） |

## 非功能需求

| 编号 | 描述 |
|------|------|
| NF1 | 非阻塞保活循环的单次间隔与资源占用须可控，**不得** 造成 Daemon CPU/连接数显著劣化（具体阈值设计阶段定义）。 |
| NF2 | 可观测性日志增量 **不得** 包含 API Key、用户消息正文等敏感信息。 |
| NF3 | 规则模板 `cursor-claw.mdc` 更新后，经 workspace 注入的新工作区应获得新保活语义（沿用既有模板注入机制）。 |
| NF4 | 变更 **不得** 破坏 CLI Agent 路径（若与 SDK 路径共用 poll 契约，设计阶段须声明影响面）。 |

## 验收标准

1. **可观测性 — error 终态**：构造或复现 SDK Run `status=error`（参考历史 `run-4dac4a72`、`durationMs≈1395228` 档），UI/开发者日志中 **可见** `run.result`、errorCode（若存在）、**末次 tool 名与状态** 中至少两项。
2. **可观测性 — 末次 shell**：保活失败场景下，日志末次 tool 记录为 **shell** 且状态为 **running**（或与实现一致的等价表述），与诊断模式一致。
3. **保活 — 23 分钟档**：在 `ch_0b1b964e` 同类 SDK 本地 Run 场景，Agent 完成回复后 **连续等待 ≥25 分钟** 无用户新消息，Run **不因** 单次 blocking poll 被 SDK 以 `error` 终止（或按 F3 优雅结束且文案正确——以设计阶段选定策略为准，本项验收 **通过标准在设计阶段与 01 对齐后锁定**）。
4. **保活 — SYSTEM OVERRIDE 衔接**：若设计保留 Daemon 25min SYSTEM OVERRIDE，超时后 Agent **继续** 保活循环，**不** 向用户发送误导性「处理失败」（除非 Run 确已终止）。
5. **文案 — 保活失败**：模拟/复现保活导致 Run error 时，用户收到 **F3.2 类** 文案，**不** 出现无区分的「请稍后重试」单独一句。
6. **文案 — 通用失败**：非保活类 tool 失败仍显示通用失败或更具体的安全文案，**不** 误用保活超时文案。
7. **文案 — 取消/过期**：用户停止与会话过期路径文案与变更前一致或通过用例回归。
8. **规则 — cursor-claw.mdc**：新注入工作区的规则描述 **非阻塞短循环保活**（或设计选定方案），且 **不再要求**「单次 poll 无限挂起」作为唯一保活手段。
9. **边界 — 飞书通道**：本变更验收 **不要求** 修改飞书排队/合并/流式行为；相关用例 **无回归**。
10. **诊断对照**：验收报告引用至少一条 Run id（如 `run-4dac4a72`）或等价日志片段，证明可观测性字段已落地。

## 方案方向摘要

| 方向 | 说明 |
|------|------|
| 可观测性 | 在 SDK 会话结束路径（`run.status === "error"`、stream 终态、status ERROR/EXPIRED）统一采集 result / errorCode / lastTool |
| 保活 | 用 **非阻塞 poll（`wait=false`）+ 短 sleep 循环** 替代 **单次 25min 级 blocking poll**；规则与 Agent 实现一致 |
| 用户文案 | 基于 **末次 tool + duration + status** 分类失败原因，映射 F3 文案表 |
| 影响面（预期） | `electron/agent-sdk.ts`、`resources/template/rule/cursor-claw.mdc`；Daemon/调度 **若需要** 再在设计阶段展开 |

## 风险与待确认

| 风险 | 说明 |
|------|------|
| SDK 超时档位未公开 | 23min/60min 来自观测，非官方文档；设计阶段需留 **降级与复测** 空间 |
| 短循环 poll 频率 | 过高增加 Daemon 负载，过低影响响应延迟；需在设计阶段定参 |
| CLI 与 SDK 双路径 | 规则变更可能影响 CLI Agent 保活；须在设计阶段声明是否同步 |
| SYSTEM OVERRIDE 语义 | 非阻塞模式下 OVERRIDE 触发频率可能变化；需验证与 SDK 循环检测误报文案的兼容 |

### 待确认项

- **类型/优先级**：初判「稳定性 / P1」，若团队有不同口径可在 design 前调整 manifest。
- **验收 3 通过标准**：「Run 不 error」与「Run error 但用户文案正确」二选一，须在 `/kb-design` 与实现对齐后写入 02-design 工程补充验收项。
