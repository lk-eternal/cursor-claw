## 背景

用户在飞书等通道与 Agent 多轮对话时，无法感知当前会话已占用多少上下文窗口，也不清楚 Agent 是否在接近上限时自动做了上下文压缩（与 Cursor IDE / CLI 中接近 limit 时的 summarization 行为一致）。

长任务、多轮补充与工具调用会快速消耗上下文；若缺少占用反馈，用户难以判断是否需要「新话题」或精简输入。同时，若 harness 未启用自动压缩，长会话可能在未预警的情况下触及上限导致任务失败。

## 目标与非目标

### 目标

1. **自动压缩**：Agent 执行过程中，当上下文接近模型上限时，由执行引擎自动触发 summarization/compression，行为与 Cursor 产品侧一致，用户无需手动执行 `/compress` 或 `/summarize`。
2. **占用可见**：每次 Agent **最终回复**末尾展示上下文占用摘要，格式清晰、一行可读，例如：`上下文：45% (90k/200k)`（具体样式以实现阶段与项目既有约定对齐）。
3. **通道覆盖**：飞书私聊、飞书群聊等经 SDK 流式/终态 notify 下发的回复路径均附带占用摘要；用户在同一产品体验下可预期看到该信息。

### 非目标

- 本期 **不** 改造飞书 CardKit 布局或新增独立卡片类型（占用信息作为正文 footer 附加即可）。
- 本期 **不** 在 Electron 设置页新增独立「上下文仪表盘」或历史曲线。
- 本期 **不** 要求用户手动触发压缩的 UI 入口（斜杠 `/compress` 若产品后续需要可单独立项）。
- 本期 **不** 定义具体模块、API 或代码结构（归属 `/kb-design`）。

## 用户与场景

### 用户

- **飞书主用户私聊 / 群聊用户**：通过飞书与 Agent 对话，希望了解本轮回复后上下文还剩多少空间。
- **运维 / 开发者**：通过 SDK UI 日志确认自动压缩是否发生，便于排查长会话异常。

### 场景 A：多轮对话后收到回复

用户已连续多轮补充需求，Agent 完成本轮任务并回复结论。用户在飞书看到的**最终正文末尾**附带一行上下文占用，例如 `上下文：62% (124k/200k)`，便于决定是否继续在同一会话追问或开启新话题。

### 场景 B：接近上限时自动压缩

会话上下文接近模型上限，执行引擎在后台自动 summarization/compression（用户不感知具体技术步骤，但会话可继续）。压缩发生后，最终回复仍附带更新后的占用摘要；开发者可在 SDK UI 日志中看到压缩相关记录以便验证。

### 场景 C：短对话首轮回复

用户仅发送一条简单问题，Agent 快速回复。占用摘要仍出现在回复末尾，百分比与绝对值应反映真实占用（通常较低），不因短对话而省略。

### 场景 D：执行失败或错误 notify

Agent Run 以错误结束并通过 notify 下发用户可见说明时，若仍有可用的占用数据，占用摘要应一并附加；若占用数据不可得，则省略 footer，**不得**用占位或误导性数字填充。

## 业务流程

### 主流程

1. **B1** 用户经飞书发送消息，Orchestrator 将任务投递给 SDK Agent。
2. **B2** Agent 执行 Run（含工具调用、多轮推理）；接近上下文上限时**自动压缩**（与 Cursor 产品行为一致）。
3. **B3** Agent 产生 assistant 最终正文；Orchestrator 经流式 CardKit 或非流式 notify 下发至飞书。
4. **B4** 在下发前的最终正文中**附加**上下文占用 footer（百分比 + 已用/上限）。
5. **B5** 用户在飞书阅读带 footer 的完整回复。

### 关键分支

- **B3-a（流式路径）**：f41Eligible 会话走 stream-text，footer 须随 **final** 包一并送达，避免中间 chunk 重复附加。
- **B3-b（非流式路径）**：不经 stream-text 的会话，footer 附在经 notify 下发的终态正文末尾。
- **B4-a（占用不可得）**：模型上限或 token 用量暂无法解析时，省略 footer，不展示错误占位。
- **B2-a（压缩发生）**：自动压缩完成后继续执行；占用摘要反映压缩后状态。

## 功能需求

### F1 自动压缩

- Agent 执行时**默认启用**与 Cursor IDE/CLI 一致的接近上限自动 summarization/compression。
- 用户无需额外配置即可生效。
- 压缩行为对用户透明（无单独飞书卡片）；可通过日志验证是否触发。

### F2 上下文占用 footer

- 附加位置：**最终回复正文末尾**（与 assistant 结论同一条消息），换行分隔。
- 展示内容：**已用百分比（整数四舍五入）** + **已用 token 与上限**（人类可读 k 单位，如 `90k/200k`）。
- 推荐格式：`上下文：{percent}% ({used}/{limit})`；若项目已有等价风格，以对齐既有约定为准。
- **中间流式 chunk 不得**重复附加 footer；仅 final 一次。

### F3 通道与路径

- **必须覆盖**：飞书 SDK 流式（stream-text final）与 SDK 终态 notify 路径。
- **CLI 路径**：IM 调度已为 SDK-only；若代码库仍存在 CLI spawn 且会下发用户可见正文，design 阶段明确是否纳入；本期产品验收以 **SDK + 飞书** 为主。

## 验收标准

1. 飞书 **主用户私聊** SDK 路径：Agent 完成一轮 Run 后，用户收到的**最终回复末尾**含上下文占用 footer，格式符合 F2。
2. 飞书 **群聊** SDK 路径（若已启用 stream-text）：同上。
3. **流式场景**：footer 仅出现在 final 包对应的消息中，中间 PATCH 不出现重复 footer。
4. **短对话**：首轮简单问答仍展示 footer，数值合理（非硬编码常量）。
5. **自动压缩**：长上下文或模拟接近上限场景下，可观察到自动压缩生效（日志或占用骤降/会话可继续）；不得因本需求关闭既有压缩能力。
6. **占用不可得**：无法解析上限或用量时，回复正常下发且**无** footer，不出现 `NaN%` 或 `undefined` 等泄漏。
7. **错误 notify**：错误路径若下发用户可见正文，行为符合 B4-a（有数据则附加，无则省略）。
8. TypeScript 编译通过；单文件行数与注释规范符合仓库 AGENTS 约定。
