# Agent失败日志崩溃分析归档产品需求文档

> **变更 ID**：`20260628165859-Agent失败日志崩溃分析归档`
> **来源**：kb-propose
> **类型**：Feature
> **优先级**：P2
> **外部 PRD**：无
> **Figma 设计图**：无
> **任务记录**：无

## 一、背景与问题

Cursor Claw 用户通过飞书等即时通讯通道与 Agent 对话。当 Agent **处理失败**（Run 报错、流式中断、调度 dispatch 失败、超时类失败等）时，飞书侧通常只收到 **一条简短友好提示**，难以据此定位根因。

**现状（已核实）**：

1. **失败检测已存在**：Electron 主进程在 SDK Run 结束为 error、流式 catch、dispatch 失败、超时 finalizer 等路径上，已调用失败通知并写入 UI 日志（如 `agent_failed`、`dispatch_failed`）。
2. **详细错误在内存与文件日志中**：`ui-logger` 维护内存 `logBuffer`（上限约 300 行），并 append 到 `daemon.log`（路径为工作区 `.cursor/daemon.log` 或 userData 下 `logs/daemon.log`）。
3. **无崩溃分析归档**：失败发生后 **未** 将相关日志片段导出到用户可访问的独立目录；设置页也 **无**「崩溃分析目录」配置项。
4. **排查成本高**：用户或支持人员需在应用内翻日志或手动找 `daemon.log`，且难以快速对齐「失败时刻前后」的上下文。

本变更在 **不改变飞书侧简短提示策略** 的前提下，为 Agent 处理失败增加 **本地崩溃分析日志归档**，便于事后排查。

## 二、目标

1. **失败触发归档**：当 Electron 判定 Agent **处理失败**（与现有失败通知同一类事件）时，自动尝试将相关日志写入用户配置的「崩溃分析」目录。
2. **按事件分目录**：每次失败在目标目录下新建子目录，命名格式为 **`yyyymmddhhmmss`**（14 位，与变更 ID 时间前缀口径一致，上海时区）。
3. **上下文日志片段**：每个事件目录内保存 **失败触发时刻对应日志行**，以及 **相邻前 30 条、后 30 条**（以内存 logBuffer 中该触发行/失败相关行为为准；不足时取现有全部，见验收标准）。
4. **可配置目录**：在应用设置中提供「崩溃分析目录」路径配置；未配置时有明确、可预期的行为（见验收标准）。

## 三、非目标

- **不改造飞书/IM 失败文案**：通道仍展示简短用户可读提示，**不**向 IM 推送完整日志或堆栈。
- **不替代现有 UI 日志与 daemon.log**：归档为 **增量能力**；应用内日志面板与 `daemon.log` 写入行为保持既有逻辑。
- **不实现远程上报或自动上传**：不向云端、飞书或第三方自动发送崩溃包；仅本地目录落盘。
- **不覆盖 daemon 进程 crash-loop 自愈**：`daemon-manager` 的自愈重启逻辑不在本 PRD 范围；本变更聚焦 **Agent 处理失败** 的日志归档。
- **不定义日志保留清理策略**：目录内历史事件的数量上限、自动清理、磁盘配额等 **不在** 本阶段必达，可在设计或后续迭代中补充。
- **不限定具体模块名与文件格式细节**：归档文件名、是否同时复制 `daemon.log` 片段等 **开放问题**，由设计阶段定案（见第八节）。

## 四、目标用户与用户故事

### 目标用户

- **日常 IM 用户**：飞书侧只看到「处理失败」类短句，需要事后自行或请他人协助排查。
- **维护与支持人员**：需要快速拿到失败前后日志上下文，而不必在 300 行 buffer 或整份 `daemon.log` 中手工检索。

### 用户故事

**故事 A：配置目录后 Agent Run 失败**

作为用户，我在设置中指定了「崩溃分析目录」。某次 Agent Run 以 error 结束，飞书仍只收到简短失败提示。我打开崩溃分析目录，看到以失败时刻命名的子目录（如 `20260628165859123`），其中有失败触发行及前后各最多 30 条相邻日志，便于对照会话与工具调用顺序排查。

**故事 B：dispatch / 流式异常失败**

作为用户，消息 dispatch 或 SDK 流式处理抛出异常导致失败。系统同样触发归档（与 Run error 等等价纳入「Agent 处理失败」），目录结构与故事 A 一致。

**故事 C：未配置崩溃分析目录**

作为用户，我尚未配置目录。Agent 失败时，飞书提示与现有一致；**不** 因归档失败而阻断失败通知或会话恢复；应用行为可预期（见验收标准：跳过归档并可选记录一条内部/UI 级提示，**不** 弹窗骚扰）。

**故事 D：在设置中修改目录**

作为用户，我在 Settings 中填写或更改崩溃分析目录路径并保存。后续新的失败事件写入新路径；**不要求** 本 PRD 迁移历史事件目录。

## 五、功能需求

### F1 失败事件与归档触发

- 归档须在 **Agent 处理失败** 时触发，覆盖与现有 `notifySdkFailure` / `notifyDispatchFailure` / 超时类失败 finalizer **同一语义** 的失败路径（具体挂接点在设计阶段对齐代码，本 PRD 要求 **不遗漏** 主路径）。
- 单次失败事件 **至多创建一次** 归档目录，避免重复 notify 导致多次 dump。

### F2 崩溃分析目录配置

- 应用配置（Settings）新增 **「崩溃分析目录」** 项：用户可指定本地绝对或相对路径（相对口径在设计阶段定义，默认可相对工作区或 userData）。
- 配置持久化于应用配置存储，重启后仍生效。
- Settings UI 在既有设置页中增加对应输入/选择控件，文案为简体中文。

### F3 按事件子目录与命名

- 在配置的根目录下，每次失败创建 **一级子目录**，目录名为失败触发时刻的 **`yyyymmddhhmmss`**（14 位；若同一秒内多次失败，设计阶段须保证 **不覆盖**，如追加毫秒或序号后缀——开放问题见第八节）。
- 子目录内至少包含 **一份** 可读的日志文本，内容为失败相关片段（见 F4）。

### F4 日志片段内容（±30 条）

- 以失败时刻在 **内存 logBuffer** 中可定位的触发行（或等价：最后一条与本次失败强相关的 UI 日志行）为锚点。
- 导出 **锚点行本身** + **之前最多 30 条** + **之后最多 30 条**（按 buffer 时间顺序）。
- 若 buffer 总量不足 61 条，则 **尽量导出全部现有行**，并在文件内或元数据中可区分「不足 30」的情况（具体格式设计阶段定）。
- 日志行内容应包含与现有 UI 日志一致的时间、级别、消息等字段，便于阅读。

### F5 未配置或不可写目录时的行为

- **未配置**崩溃分析目录：**跳过归档**，不影响失败通知与会话逻辑；允许在应用内部日志记录一条可观测信息（如「未配置崩溃分析目录，跳过归档」），**不** 向 IM 通道推送。
- **已配置但目录不存在或无写权限**：尝试创建目录；仍失败则跳过归档并记录可观测错误，**不** 阻断主失败流程。

## 六、验收标准

1. **失败触发**：在可复现的 Agent Run error、流式异常、dispatch 失败、超时失败等至少 **两类** 场景下，配置目录后均能在该目录下看到 **新增** 的 `yyyymmddhhmmss` 子目录（同一失败不重复建多个目录）。
2. **目录结构**：根目录为用户配置的「崩溃分析目录」；其下仅一层时间戳子目录；子目录内存在日志文件且可打开阅读。
3. **±30 条**：在 logBuffer 含足够条目（≥61 行且失败点居中）的用例中，归档文件包含触发行及 **恰好或至多** 前 30、后 30 条相邻行；条数边界在设计/测试中可脚本或人工计数验证。
4. **buffer 不足**：当 buffer 总行数 < 61 或失败点靠近 buffer 首尾时，归档包含 **全部可用相邻行**，无崩溃、无空文件；行为与 F4 一致。
5. **设置项**：Settings 可配置并保存崩溃分析目录；重启应用后配置仍有效；新失败写入所配路径。
6. **未配置目录**：清空或未设置目录时，Agent 失败 **仍** 正常走现有飞书短提示与 UI 日志；**不** 创建归档目录；**不** 因归档逻辑导致处理链路异常。
7. **IM 无回归**：飞书侧仍 **不** 出现完整堆栈或长日志；失败提示条数与现网策略一致（不因归档增加多条 IM 消息）。
8. **并发与幂等**：短时间连续失败或 notify 重入时，每次 **独立** 失败事件各有目录（或设计认可的防冲突命名），且单次失败不生成重复目录。

## 七、影响范围

| 范围 | 说明 |
|------|------|
| **Electron 主进程** | 失败检测既有 hook 点挂接归档；新增或扩展日志截取与写盘能力；读取配置项。 |
| **配置存储** | 应用配置模型新增「崩溃分析目录」字段及读写。 |
| **Settings UI** | 设置页新增目录配置项（输入/浏览路径）。 |
| **Preload / IPC（若需要）** | 若设置页需主进程选目录或校验路径，可能增加 IPC；具体在设计阶段确认。 |
| **不在范围** | 飞书 bot 文案、SDK 本身、daemon crash-loop 自愈、changelog/版本号（归档阶段再定）。 |

## 八、风险与开放问题

### 风险

| 风险 | 说明 | 缓解方向（设计阶段） |
|------|------|----------------------|
| **logBuffer 上限 300 行** | 失败若发生在会话早期，「前 30 条」可能少于 30；极长会话中早期上下文可能已被轮转出 buffer。 | 明确「尽量取现有」语义；可选 **同时** 从 `daemon.log` 按时间戳或行号截取补充片段。 |
| **触发行定位歧义** | 一次失败可能连续 `pushUiLog` 多行，锚点取哪一行影响 ±30 范围。 | 设计阶段定义统一规则（如最后一条 `agent_failed` / `dispatch_failed` 或 notify 前一行）。 |
| **磁盘与权限** | 用户配置系统保护目录或网络盘可能导致写失败。 | F5 跳过策略 + 内部可观测日志；不阻断主流程。 |
| **Settings 路径校验** | 非法路径、相对路径基准不一致可能导致用户困惑。 | 设计阶段定义相对路径基准与校验反馈。 |

### 开放问题（设计阶段定案）

1. **是否一并归档 `daemon.log` 片段？**  
   - 仅 logBuffer ±30 实现简单，但与文件日志可能不完全一致。  
   - 可选：额外复制 `daemon.log` 中对应时间窗口或尾部 N 行到同一事件目录（如 `daemon-tail.log`）。  
   - **本 PRD 倾向**：至少满足 buffer ±30；是否加 daemon.log 为 **设计可选增强**，需在 02-design 明确。

2. **同一秒内多次失败如何命名？**  
   - 纯 `yyyymmddhhmmss` 可能冲突。  
   - 候选：`yyyymmddhhmmss-序号`、追加毫秒、或 UUID 后缀。

3. **CLI / 非 IM 路径失败是否覆盖？**  
   - 现有 `notifyDispatchFailure` 等是否已覆盖 CLI；若存在 **不经过** 同一 notify 链路的失败，是否纳入 F1。  
   - 设计阶段对照 `agent-sdk.ts`、`finalize-sdk-run.ts` 枚举 **全部** 失败出口，列出纳入/排除清单。

4. **归档文件命名与编码**  
   - 如 `crash-context.log`、UTF-8、是否附带 JSON 元数据（sessionId、runId、失败类型）。

5. **Figma / 设置 UI**  
   - 新增一项配置，视觉沿用既有 Settings 样式即可，**无** 独立 Figma；若产品要求目录选择器样式统一，可在设计阶段引用现有设置 Tab 模式。
