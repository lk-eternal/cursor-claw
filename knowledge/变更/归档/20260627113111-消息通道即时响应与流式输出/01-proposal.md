> **优先级**：P1
> **飞书 PRD**：无
> **Figma 设计图**：无

## 背景与问题

用户通过飞书或微信向机器人发送消息后，消息会先进入处理队列，再由后台 Agent 异步领取并回复。当前体验存在明显断层：

- **入队后长时间无反馈**：从用户发消息到 Agent 开始处理之间，通道侧往往没有任何可见响应，用户容易误以为系统无响应或已崩溃。
- **处理过程不可见**：Agent 思考、启动、执行期间，用户只能等待，无法感知当前进展。
- **回复一次性到达**：Agent 产出较长内容时，用户需等到全部完成后才收到一条完整回复，等待感强、难以判断是否仍在处理。

上述问题在 Agent 冷启动、队列积压、长任务场景下尤为突出，直接影响用户对系统可靠性与响应速度的信任。

## 目标与非目标

### 目标

1. **入队即反馈**：用户消息成功进入处理队列后，在极短时间内收到明确确认，消除「是否收到」的不确定感。
2. **过程可感知**：以简洁、用户可理解的三态进度（已收到 → 处理中 → 完成）持续告知当前阶段；冷启动时补充「正在启动」说明。
3. **内容逐步可见**：在条件允许的场景下，将 Agent 产出以流式方式逐步呈现给用户，缩短首字可见时间。
4. **通道能力对齐**：充分利用各消息通道原生的「正在输入」或表情反馈能力，与文本状态互补。
5. **与现有通知整合**：入队确认替代冷启动前的沉默；调整现有启动提示文案，避免连续两条含义相近的通知。

### 非目标

- 不向用户暴露工具调用、内部步骤、错误堆栈等技术细节。
- 本期不追求 CLI 模式、群聊场景的完整流式体验（可降级为分段发送或保持现状，列入二期）。
- 不改变消息入队、会话路由、指令拦截等既有业务规则的本质逻辑。
- 不涉及 Electron 设置界面、通道凭据配置等桌面端 UI 改造。

## 用户与场景

### 场景 A：单条消息、Agent 已在运行

用户发送一条私聊消息。系统立即回复「已收到，正在处理」并展示通道原生进行中状态；Agent 领取后进入「处理中」；流式场景下内容在同一条消息中逐步更新；完成后进入「完成」态并停止进行中指示。

### 场景 B：连发多条消息（同一会话）

用户短时间内连续发送多条消息。每条消息均单独收到入队确认；若同一会话排队数超过 1 条，确认文案中附加排队提示（如「前面还有 N 条待处理」），让用户知晓顺序而非重复焦虑。

### 场景 C：Agent 冷启动

用户发消息时 Agent 尚未运行。入队确认立即发出（替代原先启动前的沉默）；随后若需等待 Agent 启动，附加「正在启动」状态说明；启动完成后统一为「Agent 处理中…」，不再与入队确认形成两条近义重复通知。

### 场景 D：长任务 / 慢回复

Agent 处理耗时较长。用户持续看到「处理中」及通道原生进行中指示；若支持流式，首段内容在合理时间内可见；不支持流式时，可按段落或节流策略分段发送，避免长时间完全无输出。

### 场景 E：群聊

群聊消息仍须满足既有 @ 机器人等触发规则。本期优先保障入队确认与三态进度；流式输出列为二期或降级为任务完成后一次性回复。

### 场景 F：主用户私聊（SDK 模式，优先流式）

主用户与机器人的私聊会话，且后台以 SDK 方式运行 Agent 时，作为流式输出的首选场景：单条消息持续更新为首选展示形态。

## 现状简述

- 用户消息经飞书 WebSocket 或微信长轮询进入系统后写入队列，**入队本身不向用户发送任何确认**。
- Agent 通过轮询领取消息后才开始处理；飞书通道在首次领取时会对原消息添加「已领取」类表情反馈，微信通道可在收发过程中展示「正在输入」状态——但这些反馈**发生在 Agent 领取之后**，无法覆盖入队到领取之间的空窗期。
- Agent 启动前系统可能向用户推送等待类提示，与理想的「入队即确认」时序重叠，且文案与入队确认语义接近，易造成重复感。
- Agent 回复目前以**完整消息一次性发送**为主；SDK 模式虽具备流式产出能力，尚未系统化地传递到消息通道呈现给用户。

## 功能需求

### 1. 入队即时确认

| 编号 | 需求描述 |
|------|----------|
| F1.1 | 用户消息通过通道校验并成功写入处理队列后，**必须在 3 秒内**向该用户发送简短文本确认，默认文案为「已收到，正在处理」。 |
| F1.2 | 确认消息针对**每一条**成功入队的用户消息单独发送，不因同会话内已有 Agent 在运行而省略。 |
| F1.3 | 同一会话内排队消息数大于 1 时，在确认文案中附加排队提示，告知用户当前前面还有待处理条数（N ≥ 1）。 |
| F1.4 | 消息被指令系统拦截、未进入常规定义的处理队列时，不适用本条的入队确认规则（沿用既有指令反馈逻辑）。 |

### 2. 通道原生进行中指示

| 编号 | 需求描述 |
|------|----------|
| F2.1 | 入队确认发出后，同步触发该通道支持的「进行中」原生反馈：微信展示「正在输入」；飞书在可行时使用与「处理中」语义一致的表情或等价反馈。 |
| F2.2 | 原生进行中指示的生命周期与下文状态机绑定：进入「完成」态或最终回复发送完毕后停止；异常中断时也须停止，避免长期悬挂。 |
| F2.3 | 通道不支持某类原生反馈时，仅依赖文本状态，不强行模拟不可用的能力。 |

### 3. 处理过程状态（三态 + 冷启动）

| 编号 | 需求描述 |
|------|----------|
| F3.1 | 对用户可见的处理进度统一为三态：**已收到** → **处理中** → **完成**。 |
| F3.2 | Agent 尚未运行、需要冷启动时，在「已收到」之后、「处理中」之前，可展示 **正在启动** 附加说明；该说明为可选子阶段，不替代三态主流程。 |
| F3.3 | 「处理中」阶段的对外文案统一为 **「Agent 处理中…」**，用于替代现有启动等待类提示，避免与入队确认「已收到，正在处理」形成连续两条近义通知。 |
| F3.4 | 状态文案与指示均不得包含工具名称、内部步骤、队列文件名、进程信息等用户不可理解的内容。 |
| F3.5 | 「完成」态可在最终回复送达后通过停止进行中指示、或通道既有的「已完成」类反馈（如飞书完成表情）体现；不要求额外发送纯状态文本，除非通道能力需要。 |

### 4. 流式输出

| 编号 | 需求描述 |
|------|----------|
| F4.1 | **优先适用范围**：SDK 模式 + 主用户私聊会话。 |
| F4.2 | **首选展示形态**：在同一条 outbound 消息上持续更新内容，使用户尽早看到 Agent 产出的开头部分，并随产出增长而更新；**飞书通道优先采用 CardKit 流式卡片**实现同条持续更新（Rev1）。 |
| F4.3 | **降级策略**：当通道不支持单条消息编辑更新时，按自然段落或节流策略分段发送多条消息，仍优于「全部完成后一次发送」。 |
| F4.4 | **二期或降级范围**：CLI 模式运行 Agent、群聊会话——本期可不实现完整流式，维持任务完成后一次性回复或分段降级；须在验收中明确本期边界。 |
| F4.5 | 流式内容与最终完整回复在语义上应一致；流式结束后用户看到的终态内容不应少于非流式场景下的完整回复（允许排版差异，不允许实质信息丢失）。 |

### 5. 与现有通知的整合

| 编号 | 需求描述 |
|------|----------|
| F5.1 | 入队即时确认承担「让用户知道消息已收到」的职责，**替代** Agent 冷启动前通道侧的沉默期。 |
| F5.2 | 原「启动等待」类通知改为「Agent 处理中…」，且仅在 Agent 真正进入处理阶段时呈现，不与入队确认重复刷屏。 |
| F5.3 | 飞书「已领取」「已完成」表情反馈与新的三态进度并存时，语义应一致、不互相矛盾；若重复，以用户可理解的文本状态为主、表情为辅。 |

## 通道差异与降级

| 能力 | 飞书 | 微信 | 本期策略 |
|------|------|------|----------|
| 入队文本确认 | 支持 | 支持 | 两通道均必须实现 |
| 原生进行中指示 | 表情反馈 | 正在输入 | 有则用，无则仅文本 |
| 单条消息持续更新 | 待验证/可能受限 | 待验证/可能受限 | 不支持则段落分段 |
| 完成态反馈 | 已完成表情（既有） | 停止正在输入 | 沿用并纳入状态机 |
| 流式输出 | 主用户私聊 SDK 优先 | 同左 | CLI/群聊二期 |

## 会话与消息规则

1. **会话隔离**：状态反馈与流式输出均绑定到触发消息所属的会话，不跨会话串台。
2. **顺序感知**：同会话内多条消息按入队顺序处理；排队提示仅反映队列深度，不改变实际处理顺序。
3. **重复消息**：若通道重复投递同一条用户消息且被系统去重拒绝入队，不发送入队确认。
4. **Agent 已在运行**：新消息仍须入队确认；若当前已有任务在处理，排队提示准确反映等待条数。
5. **失败与超时**：Agent 启动失败或处理异常终止时，须停止进行中指示，并向用户发送可理解的失败说明（沿用既有错误通知规范，本期不展开细节）。

## 文案与状态机

### 标准文案

| 阶段 | 用户可见文案 / 指示 |
|------|---------------------|
| 入队确认 | 「已收到，正在处理」；排队时附加「前面还有 N 条待处理」 |
| 正在启动（冷启动） | 「正在启动」或与三态兼容的简短说明 |
| 处理中 | 「Agent 处理中…」+ 通道原生进行中指示 |
| 流式输出 | Agent 产出内容本身（逐步可见） |
| 完成 | 停止进行中指示；可选已完成类原生反馈 |

### 状态流转（业务视角）

```
用户发消息
  → [已收到] 入队确认（≤3s）+ 原生进行中指示（可用时）
  → [正在启动]（仅冷启动）
  → [处理中] 「Agent 处理中…」
  → [流式输出]（SDK 主用户私聊优先，可选）
  → [完成] 终态回复就绪，停止进行中指示
```

## 非功能需求

| 编号 | 描述 |
|------|------|
| NF1 | 入队确认延迟：P95 ≤ 3 秒，P99 ≤ 5 秒（从消息通过校验到用户收到确认）。 |
| NF2 | 流式首段可见：SDK 主用户私聊场景下，Agent 开始产出后 P95 ≤ 10 秒内用户可见首段内容（流式或分段降级均计）。 |
| NF3 | 状态指示及时停止：任务完成或失败后 5 秒内停止所有进行中类指示，避免「假死输入中」。 |
| NF4 | 文案统一为简体中文，语气简洁、非技术化。 |
| NF5 | 连发 5 条消息时，每条均独立确认，排队计数准确，无遗漏、无重复确认同一条。 |
| NF6 | 流式更新频率应节流，避免通道限流或用户端消息风暴（具体频控在设计阶段定义，本期要求「可感知流畅」且「不刷屏」）。 |

## 验收标准

1. **入队确认 SLA**：在飞书私聊、微信私聊各至少 10 次实测中，消息成功入队后 **100%** 在 **3 秒**内收到「已收到，正在处理」或等价确认；P95 延迟 ≤ 3 秒。
2. **排队提示**：同会话连续发送 3 条消息，第 2、3 条确认中 **均包含** 正确的排队条数提示（第 2 条提示前还有 1 条，第 3 条提示前还有 2 条，或符合实际队列深度的等价表述）。
3. **冷启动体验**：Agent 未运行状态下发送 1 条消息，用户在 **3 秒内** 收到入队确认；冷启动期间可见「正在启动」或等价说明；Agent 进入处理后仅出现 **一条**「Agent 处理中…」类处理中通知，**不出现**与入队确认语义重复的双条近义通知。
4. **三态完整性**：至少 5 次端到端成功任务中，用户可感知「已收到 → 处理中 → 完成」完整链路；全程 **无** 工具名、内部步骤等泄露。
5. **原生进行中指示**：微信私聊场景下，处理过程中 **可见**「正在输入」；任务完成后 **10 秒内** 输入状态消失。飞书场景下，处理中 **可见**与处理语义一致的表情或等价反馈（若通道支持）。
6. **流式输出（SDK + 主用户私聊）**：至少 3 次长回复任务中，用户在 Agent 开始产出后 **10 秒内** 看到首段内容；终态完整内容与一次性发送模式相比 **无实质信息缺失**。
7. **流式降级**：在不支持单条更新的通道或模拟受限环境中，长回复 **仍能在 10 秒内** 以分段形式呈现首段内容，而非等待全部完成。
8. **本期边界**：CLI 模式或群聊场景 **不要求** 完整单条流式更新，但 **仍须满足** 入队确认与三态进度（F1、F3）；验收报告明确标注通过/不适用。
9. **异常停止指示**：模拟 Agent 启动失败或处理中断，**5 秒内** 停止所有进行中指示，用户收到可理解的失败或异常说明（沿用既有规范）。
10. **无重复确认**：同一条用户消息仅触发 **一次** 入队确认；去重拒绝入队的重复投递 **不发送** 确认。
