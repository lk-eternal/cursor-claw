## 背景与问题

Cursor Claw 用户通过飞书、微信等即时通讯通道与 Agent 对话，由后台调度 Agent 处理用户消息。当 Agent 执行较长任务（如多步工具调用、复杂检索与生成）时，可能触发 **Run 超时**——即单次 Agent 运行超出平台或产品允许的最长处理时间。

**现状问题**：

1. **超时后系统未终止 Run**：Run 超时后，系统未能结束当前运行；会话仍停留在「处理中」或异常占用状态，用户侧往往 **看不出** 任务已结束。
2. **并非超时当下就在通道报错**：超时发生时，消息通道 **通常不会** 立即、持续地推送失败或技术报错；用户容易误以为任务仍在进行或已静默结束。
3. **稍后发消息导致处理失败**：用户 **等到过了超时间隔之后** 再发送新消息时，Agent **无法正常受理** 该消息，处理失败。
4. **须手动 Stop 与 Reset 才能恢复**：出现上述失败后，用户需依次执行 **停止 Agent（Stop）** 与 **重置（Reset）**，才能将会话恢复到可继续对话的空闲状态。

已有部分超时场景的友好提示文案，但 **停止与恢复链路仍不完整**——超时后 Run 与会话状态未同步收尾，用户稍后发消息仍会撞车。本变更聚焦 **超时发生时的自动停止与会话恢复**，使用户无需 Stop/Reset 即可继续对话。

## 目标用户与场景

### 目标用户

- **IM 通道日常用户**：通过飞书/微信与 Agent 交互，期望对话连贯、失败后能直接重试或换话题。
- **长任务使用者**：发起需要较久完成的请求（如大范围代码分析、多轮工具协作），更容易触及超时边界。

### 场景 A：长任务处理中超时

用户发送一条复杂请求，Agent 开始处理并在通道展示进度或流式输出。处理时间超过允许上限后 Run 超时。用户期望：系统 **立即停止** 当前任务，会话回到 **可发新消息** 的空闲状态。**现状**：Run **未被终止**，会话仍停留在处理中或异常占用状态；超时当下 **通常没有** 明显的持续报错提示。

### 场景 B：超时未终止后稍后发消息（核心场景）

接场景 A，用户 **并未立刻** 察觉异常，在 **过了超时间隔之后** 才发送下一条消息（如简化需求或换一个问题）。用户期望：新消息被正常受理，Agent 开始新一轮处理。**现状**：Agent **处理失败**，用户无法继续对话；须先 **Stop Agent**，再 **Reset**，会话才能恢复。

### 场景 C：恢复后的正常继续

接场景 B，若本变更生效：超时判定后系统 **自动停止 Run 并恢复会话为空闲**；用户 **无需** Stop/Reset，直接发送新消息即可正常启动新一轮处理，**不** 被上一轮超时残留状态阻塞。

### 场景 D：与保活等待场景区分

用户在一轮回复完成后长时间未发新消息，会话进入「等待下一条消息」的保活阶段；若该阶段因超时结束，已有或并行的保活类文案逻辑可继续适用。本变更 **同时覆盖** 任务执行中的 Run 超时，但 **不要求** 在本 PRD 中重新定义保活策略本身（保活兼容见关联变更「SDK 保活与 Run 生命周期兼容」）。

## 功能需求

### F1 超时自动停止 Run

- 当系统判定当前 Agent Run 因 **超时而失败或应终止** 时，须 **立即自动停止** 该 Run，不得依赖用户手动 Stop。
- 停止动作须与会话调度状态一致：停止后不再继续向 IM 通道推送该 Run 的进度、流式片段或后续工具结果。

### F2 会话自动恢复为可继续使用

- Run 因超时自动停止后，对应 IM 会话须 **自动恢复为空闲（idle）**，用户可直接发送新消息发起新一轮处理。
- 用户 **无需** 执行 Reset 或等价的手动「清会话状态」操作即可继续使用同一会话（同一会话标识、同一通道上下文）。
- **核心验收路径**：超时后用户 **稍后** 发送新消息时，Agent 须 **正常受理**，不得再现「须 Stop + Reset 才能恢复」的现状。

### F3 消息通道防护（非主诉，验收兜底）

- 超时场景下，**禁止** 向用户 IM 通道下发技术堆栈、内部错误码、原始平台报错等不可读内容。
- **禁止** 对同一超时事件重复、连续推送多条失败通知。
- 超时停止后，通道侧「处理中 / 进行中」类状态须 **同步结束**，避免用户误以为任务仍在运行。
- 本项为 **防护性要求**：主诉是超时未终止导致稍后发消息失败，而非超时当下通道持续报错。

### F4 可选简短友好提示（一次且结束进度展示）

- 若产品需要用户感知超时原因，允许发送 **一条** 简体中文友好提示，语义包含：**本次处理已因超时结束**、**可重新发送消息继续**。
- 提示发送后 **不得** 再追加同义失败消息；进度条、typing、流式占位等展示须在该轮超时收尾时 **停止**。
- 友好提示 **不得** 替代 F1/F2：仅有文案而无自动停止与会话恢复 **不满足** 本需求。

## 边界与不在范围

- **用户主动取消**：用户点击 Stop 或发送取消类指令的路径，沿用既有行为；本变更 **不** 将主动取消与超时停止混为一谈。
- **非超时类失败**：工具异常、网络中断、通道不可用、权限拒绝等 **非超时** 失败，沿用或另行定义既有失败路径；本 PRD **不** 要求统一所有失败类型的文案与恢复策略。
- **CLI / 非 IM 路径**：若存在不经过飞书/微信 IM 的 Agent 入口，本变更 **优先保证 IM 调度路径**；CLI 是否对齐在设计阶段评估，非本 PRD 必达项除非验收明确纳入。
- **调整超时阈值本身**：是否延长或缩短平台允许的最长处理时间 **不在** 本变更范围；本变更解决的是 **超时已发生时的停止与恢复**。
- **新增设置页或 Figma 界面**：无新增页面；不涉及视觉设计（Figma：无）。
- **技术实现细节**：本阶段 PRD 不限定具体模块、接口或日志字段；设计阶段再展开。

## 验收标准

1. **自动停止**：在可复现的 Run 超时场景下（长任务或测试环境模拟超时），系统在超时判定后 **数秒内** 自动结束 Run，**无需** 用户点击 Stop；会话 **不** 长期停留在处理中或异常占用状态。
2. **稍后发消息可继续（核心）**：上述场景结束后，用户 **等待超时间隔过后** 在同一会话发送新消息，**不执行 Stop/Reset**，新 Run **正常启动** 并产生回复（或明确的非超时类失败，但 **不** 被上一轮超时残留状态阻塞）。
3. **无需手动恢复**：超时自动停止与会话恢复完成后，用户 **不需要** 依次执行 Stop Agent 与 Reset 即可继续使用同一会话。
4. **通道防护（兜底）**：超时场景下，用户 IM 通道 **不出现** 堆栈、原始 error 对象或内部错误码；同一超时事件触发的用户可见失败/提示 **不超过一条**；停止后 **无** 长期「处理中」展示。
5. **友好提示（若启用）**：若实现 F4，文案为简体中文、语义符合 F4，且与「请稍后重试」类 **通用失败** 文案可区分（超时类应体现「已自动结束、可重发消息」）。
6. **主动取消无回归**：用户主动 Stop 后，行为与变更前一致或通过用例回归；**不** 误走超时自动恢复逻辑导致状态错乱。
7. **非超时失败无回归**：任选一条非超时失败用例（如故意触发工具失败），确认 **不** 误用超时专用文案，且既有失败路径仍可用。
