# 知识库内容规范

> 本文件是**知识文件与变更文档内容结构的唯一标准**。kb 流程（`/kb-*`）生成或维护业务域知识文件、变更目录内 `02-design.md` / `03-tasks.md` 时，内容结构以本文件为准。

## 一、业务域文件组织

每个业务域目录（`knowledge/业务域/<中文领域>/`）统一采用：

```
<领域>/
├── 00-README.md    # 领域局部索引：文件清单、职责边界、推荐阅读路径（编号 00）
├── 01-概览.md       # 模块总图（结构见「三」）
├── 02-<子模块>.md   # 编号子模块文件（十段式，结构见「二」）
├── 03-<子模块>.md
└── 0N-<子模块>.md
```

- README 编号为 `00`，排在 `01-概览` 之前。

- **按「子模块/能力」拆分，不按「角色」拆分**：不再使用 `客户端流程.md`、`后台流程.md`、`架构.md`、`接口.md`、`数据.md` 这类按角色分文件的写法；客户端流程、接口、数据等作为**段落**写进各子模块文件，跨子模块的聚合视图放进 `01-概览`。
- **编号前缀按阅读优先级**：`01` 概览必为第一篇，其后按推荐阅读顺序编号（如房间域 `Feed → 进房 → 麦位/成员/公屏/礼物 → 关注 → 后台运营`；账户域 `登录 → 注册 → 邮箱安全 → 注销 → … → 资料 → 关系 → 举报`）。
- **概览必须链接全部子模块**；`00-README.md` 维护文件清单与阅读路径。
- **默认扁平，不建子目录**：同一业务域内所有编号子模块文件直接放在 `<领域>/` 根下（如 [账户](../业务域/账户/00-README.md)、[房间](../业务域/房间/00-README.md)、[钱包](../业务域/钱包/00-README.md)）。按能力连续编号即可，**不必**再按「认证/用户」等业务子域拆中文子目录。
- **子目录仅作例外**：仅当编号子模块已拆到仍超限（单文件 >3000 字符且无法再拆）或独立主题体量极大时，才允许中文子目录分组；子目录内文件**仍遵循编号 + 十段式**，并维护子目录 `README.md`（子目录不设 `00-` 前缀）。`00-README.md` 只链子目录入口，**不得**在领域 README 中展开子目录叶子清单。

## 二、工程平台分区组织

每个工程平台分区（`knowledge/工程平台/<中文平台分区>/`）与业务域采用**同一套编号与内容结构**：

```
<平台分区>/
├── 00-README.md    # 分区局部索引：文件清单、职责边界、推荐阅读路径（编号 00）
├── 01-概览.md       # 端工程总图（结构见「四」）
├── 02-<子模块>.md   # 编号子模块文件（十段式，结构见「三」）
└── 0N-<子模块>.md
```

- 分区示例：`Flutter客户端/`、`Rust服务端/`、`Quasar管理后台/`、`QuasarH5/`、`官方网站/`、`Proto协议/`。
- **禁止**在分区内使用无编号的 `README.md`（根目录 `00-README` 除外）、`概览.md` 等旧命名；`工程平台/README.md`（根入口）只列各分区 `00-README.md`，不展开叶子文件。
- 子模块按**该端工程的阅读优先级**编号（如 Rust：`概览 → 对象存储 → 错误 i18n → 版本检测 → 可观测`）。
- 纯前端分区（Flutter/Quasar/H5/官网）的十段式中：「三、服务端规则」无服务端实现时写「无」；构建、路由、工程约定写入「二、设计决策与取舍」或「四、客户端流程」。
- 工程平台子模块同样遵守「每文件 ≤ 3000 字符」与「以代码为准」。

## 三、子模块文件结构（十段式）

每个编号子模块文件统一十段式，**标题用中文「一、二、三…」**；某段在本子模块确无内容时写「无」，不为凑结构注水：

| 段 | 标题 | 内容 |
|---|---|---|
| 一 | 能力范围 | 本子模块负责什么、不负责什么 |
| 二 | 设计决策与取舍 | 为什么这样设计、权衡了什么（**回代码核实**，见「四」） |
| 三 | 服务端规则 | 业务逻辑、规则、约束、状态流转 |
| 四 | 客户端流程 | 用户侧/后台侧流程；关键链路配 mermaid |
| 五 | 接口 | 方法 + 关键入参/出参/错误码 |
| 六 | 数据 | 表/字段；必要时配关系图 |
| 七 | 非功能与可观测 | 并发、容错、安全/权限、关键日志/埋点 |
| 八 | 推送 | 推送类型与触发；无则写「无」 |
| 九 | 已知限制与 TODO | 集中沉淀限制、未覆盖、待办 |
| 十 | 变更记录 | 按日期记结构性变更摘要 |

## 四、概览文件结构（`01-概览.md`）

概览是模块总图，不套用十段式，但**段落顺序、中文编号、必填项固定**，不得自行增删或调换顺序；某段在本领域确无内容时写「无」，不为凑结构注水：

| 段 | 标题 | 必填 | 必配图 | 内容 |
|---|---|---|---|---|
| 一 | 模块定位与边界 | 是 | 否 | 模块职责，含对外部领域的引用边界 |
| 二 | 整体架构 | 是 | **是**（mermaid） | 分层/多链路总图 |
| 三 | 核心状态机/主流程 | 是 | **是**（mermaid） | 领域主状态机或主流程；确无则写「无」并说明原因 |
| 四 | 子模块清单 | 是 | 否 | 功能模块表，逐条链接各编号子模块 |
| 五 | 关键约束 | 是 | 否 | 全局性硬约束 |
| 六 | 术语表 | 是 | 否 | 领域专有名词集中定义，子模块直接引用、不重复定义 |
| 七 | 依赖关系 | 是 | **是**（mermaid） | 对其他领域的引用，配依赖图 |
| 八 | 全局非功能与可观测 | 是 | 否 | 全局并发/容错/安全/权限/日志/埋点 |
| 九 | 全局已知限制 | 是 | 否 | 领域级限制与未覆盖项 |
| 十 | 文档入口 | 是 | 否 | 编号子模块清单（有序链接），不与「四」合并 |
| 十一 | 变更记录 | 是 | 否 | 按日期记结构性变更摘要 |

- 标题统一用中文「一、二、三…」编号，顺序与上表一致。
- 「二」「七」必须配 mermaid 图；「三」原则上配图，确无主状态机/主流程时写「无」并一句话说明。
- 「四 子模块清单」与「十 文档入口」职责不同：前者是「模块→职责」表，后者是有序阅读入口清单，**不得合并省略**。

## 五、变更设计文档结构（`02-design.md`）

`/kb-design` 产出；**段落顺序、中文编号、必填项固定**，不得自行增删或调换顺序；某段确无内容时写「无」：

| 段 | 标题 | 必填 | 必配图 | 内容 |
|---|---|---|---|---|
| 一 | 业务流程与改动范围 | 是 | **是**（业务流程 mermaid） | 含「业务流程图」「流程步骤与改动对照」表、「改动汇总」；对照表须含步骤 ID、改动类型、落点文件、01 验收关联 |
| 二 | 整体思路 | 是 | 否 | 根因、方案要点、与 01 的追溯 |
| 三 | 分层设计 | 是 | 可选（分层 mermaid） | 端点/服务/数据层落点；**不能**替代「一」的业务流程图 |
| 四 | 接口设计 | 是 | 否 | 方法 + 关键入参/出参/错误码；无变更写「无」 |
| 五 | 数据结构 | 是 | 否 | 表/字段/模型扩展；无变更写「无」 |
| 六 | 实现步骤 | 是 | 否 | 有序步骤；每步可回溯「一」中步骤 ID |
| 七 | 参考实现 | 是 | 否 | CodeGraph 或源码命中的关键符号与路径 |
| 八 | 技术影响 | 是 | 否 | 涉及模块、proto/数据变更、风险；可含「工程补充验收项」子节 |
| 九 | 知识库影响 | 是 | 否 | 初评：哪些知识文件可能受影响 |
| 十 | 知识库更新计划 | 是 | 否 | 分「（一）必须更新 / （二）可能更新 / （三）不需要更新」三小节；archive 主消费清单 |

**编号规则（大段 + 段内小节，均可固定引用）**：

| 层级 | Markdown 标题 | 示例 | 引用写法 |
|---|---|---|---|
| 大段 | `## 一、` … `## 十、` | `## 八、技术影响` | `八` 或 `§八` |
| 段内小节 | `### （一）` … `### （三）` | `### （二）工程补充验收项` | `八·（二）` 或 `§八·（二）` |

- 段内用**括号中文数字** `（一）（二）…`，与同文件大段 `一、` 区分；**禁止**段内再用 `### 一、` 或与语义绑死的无序号标题（如单独 `### 业务流程图`）。
- 含段内小节的固定结构：

| 大段 | 段内小节（顺序固定） |
|---|---|
| 一 | （一）业务流程图；（二）流程步骤与改动对照；（三）改动汇总 |
| 八 | （一）影响范围；（二）工程补充验收项 |
| 十 | （一）必须更新；（二）可能更新（视实现结果）；（三）不需要更新 |

- 二～七、九 无段内小节，正文直接写在对应 `##` 下；确无内容写「无」。
- 「一·（一）」内 mermaid 节点须用图例标注 `不改` / `改动` / `新增` / `删除`。
- 纯知识库同步类变更若无用户可见业务流，「一·（一）」可用数据/配置流转图替代，但须在「一·（二）」对照表说明原因。

## 六、变更任务文档结构（`03-tasks.md`）

`/kb-plan` 产出；文件级**仅两段**，顺序固定：

| 段 | 标题 | 内容 |
|---|---|---|
| 一 | 执行计划 | `### （一）依赖图`；`### （二）分组调度` |
| 二 | 任务清单 | 若干 `## T{n}: {名称}` 任务块 |

每条 `T{n}` **必须**含以下字段（用 `###` 子标题，顺序固定）：背景、上下文文件、实现范围、接口契约、验收标准、依赖。

- 单条任务须自包含：子 agent 只读该 `T{n}` + 上下文文件即可开工，**不应**回读 `02-design.md`。
- 每条任务验收标准须能覆盖 `01` 验收与 `02`「八·（二）工程补充验收项」（若有；兼容旧版 `### 工程补充验收项`）。

## 七、内容规则

1. **以代码为准**：「设计决策与取舍」「非功能与可观测」等结论必须回 `kb.project.json` 中 `codeRoots` 所列目录核实并标注依据位置；查不到依据的结论标「（待确认/推测）」，**严禁编造**。
2. **中文编写**：所有知识文件、注释、文档使用简体中文。
3. **中文标题分级**：大标题用「一、二、三…」。
4. **关键链路可视化**：状态机、时序、架构、数据关系优先用 mermaid（节点 ID 不带空格，特殊字符 label 用双引号，不用 `end` 等保留字做 ID，不写显式颜色）。
5. **每文件 ≤ 3000 字符**：超限拆分为多个编号子模块文件。
6. **不臆改业务语义**：重组/补全文档时保留既有事实，产品意图不清先问用户。
7. **变更记录**：结构性改动在「十、变更记录」按日期追加一句摘要。
